🔋 Background Execution Limits: What the OS Actually Lets You Do

"Schedule a background refresh every 15 minutes" is a request you file, not a promise the OS keeps. Understanding why turns mysterious "it works on my phone but not my user's" bugs into predictable behaviour.

Mobile Development · ~8 min read · updated August 2026

TL;DR — Both platforms treat background CPU time as a scarce, rationed resource, not something your app owns. iOS grants short bursts through specific APIs (background modes, BGTaskScheduler) and decides if and when to honour a scheduled request based on usage patterns and battery. Android's Doze mode and background-execution limits do the same with WorkManager. Design every background task assuming it might run late, run rarely, or not run at all — and make the foreground path the one that's actually reliable.

1 · Why the OS rations background time at all

A phone's battery and thermal envelope are shared across every app the user has installed. If each app could run freely in the background — polling servers, keeping radios awake, holding CPU — the device would be dead by lunchtime. So both platforms flipped the default: background execution is off unless you ask for a specific, narrow capability, and even then the OS reserves the right to say no.

Mental model: foreground execution is a lease you hold as long as you're on screen. Background execution is a favour the OS grants in small, unpredictable doses, sized to how much it trusts your app not to abuse it.

2 · iOS: named capabilities, not a general "run in background"

There is no API on iOS for "keep running in the background." Instead you declare one or more specific UIBackgroundModes, each unlocking a narrow, purpose-built capability:

Background modeWhat it actually grants
fetchPeriodic short wake-ups to refresh content — frequency chosen by the system, not you.
remote-notificationA few seconds of runtime when a silent push arrives (see the push notifications article).
audio, location, voipGenuinely continuous background execution — but only while actively playing audio, tracking location the user opted into, or holding a VoIP call.
processing (BGTaskScheduler)Longer, deferrable maintenance work (minutes), usually while charging and on Wi-Fi.
iOS · Swift — BGTaskScheduler
func scheduleCleanup() {
  let request = BGProcessingTaskRequest(identifier: "com.example.cleanup")
  request.requiresNetworkConnectivity = true
  request.requiresExternalPower = true          // hint, not a hard rule the OS must obey
  request.earliestBeginDate = Date(timeIntervalSinceNow: 3600)
  try? BGTaskScheduler.shared.submit(request)
  // The system decides WHEN — or IF — this actually runs, based on
  // battery level, how often the user opens the app, and system load.
}
Every request is advisory. earliestBeginDate means "not before this time," never "at this time." An app the user opens twice a week gets far fewer background opportunities than one they open twelve times a day — the OS is actively learning and rationing per app.

3 · Android: WorkManager on top of Doze and App Standby

Android's story is the same shape with different names. Doze mode kicks in when the device is stationary and unplugged for a while: network access, sync, and jobs are batched into short "maintenance windows" instead of running whenever requested. App Standby Buckets further throttle how often a specific app gets to run background jobs based on how recently and often the user engages with it — an app in the "rare" bucket might get one job execution window a day.

Android · Kotlin — WorkManager
val constraints = Constraints.Builder()
    .setRequiredNetworkType(NetworkType.CONNECTED)
    .setRequiresBatteryNotLow(true)
    .build()

val request = PeriodicWorkRequestBuilder<SyncWorker>(15, TimeUnit.MINUTES)
    .setConstraints(constraints)
    .build()

// "15 minutes" is a MINIMUM interval, not a guarantee — Doze and the
// standby bucket can and will stretch it out much further.
WorkManager.getInstance(context).enqueue(request)

WorkManager's real value isn't scheduling precision — it's that it survives app restarts, reboots, and picks the right underlying mechanism (JobScheduler, or a fallback) for you. It never promises a specific wall-clock time.

4 · The battery budget mental model

Think of every background wake-up as spending from a shared budget the OS is protecting on the user's behalf, not one your app owns:

  • Radio wake time is the expensive line item. Turning on the cellular or Wi-Fi radio from an idle state costs far more energy than the few hundred milliseconds it's actually transmitting. Batch network calls so one wake-up does several jobs' worth of work.
  • Engagement is currency. Both platforms give more generous background allowances to apps the user actually opens often. An app that never gets opened accrues almost no background trust.
  • Charging + Wi-Fi is the OS's preferred moment. Heavy, deferrable work (cleanup, large downloads, analytics upload) should be flagged as such so the system can slot it into a moment that costs the user nothing they'd notice.

5 · Designing work that survives being rationed

Once you accept that background execution is opportunistic, the design shifts from "make sure this runs" to "make sure it's fine whenever it eventually runs — or doesn't":

Pattern: keep a local "next required sync" timestamp. On every app foreground, cold start, and successful background wake, check it and catch up if stale — rather than relying on any single background trigger to be the one that fires.
  • Make tasks resumable, not atomic-or-nothing. A background window can end mid-task; checkpoint progress so a retry continues instead of restarting.
  • Never gate correctness on a background task firing. The foreground reconciliation path (open app → sync) is the one guarantee you actually have.
  • Prefer push-triggered work over polling. A silent push that says "come sync" costs the OS's battery budget only when there's actually something new — a 15-minute poll spends budget constantly, whether or not anything changed.
  • Respect explicit hints. requiresExternalPower, requiresBatteryNotLow, and Doze-maintenance-window constraints exist so the system can trust you — abuse them (or work around them with foreground-service tricks) and the platform quietly downgrades your app's standing.

6 · Quick checklist

  • ✅ Declare the narrowest background mode / constraint set that covers the actual need.
  • ✅ Treat every scheduled time as "earliest," never "exact."
  • ✅ Batch network work into as few radio wake-ups as possible.
  • ✅ Reconcile on foreground as the guaranteed catch-up path.
  • ✅ Make background tasks resumable across a killed process.
  • ❌ Don't rely on precise interval scheduling for anything user-facing.
  • ❌ Don't fight Doze/App Standby with background-service workarounds — it erodes the OS's trust in your app.

7 · Key takeaways

iOS and Android converged on the same answer from different directions: background execution is a rationed, opportunistic favour, sized by how much the OS trusts your app and how much budget it has to spare. Build features so the foreground path is where correctness lives, and let background work be the pleasant surprise when the OS decides to grant it — not the thing your app depends on.
