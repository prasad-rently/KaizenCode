📦 The Courier

RPC frameworks, as a category — not just gRPC. Why "call it like a local function" won over raw sockets, where this pattern quietly runs your day, and the tradeoffs and vulnerabilities that come with the convenience.

1What RPC actually is

Every backend eventually needs Service A to ask Service B to do something and hand back an answer. You could open a raw TCP socket and invent your own byte format — and early distributed systems did exactly that, painfully, for every single service pair. RPC (Remote Procedure Call) is the idea that this should feel like calling a normal function: paymentService.charge(orderId, amount) reads exactly like a local method call, but under the hood it's serialized, sent across the network, executed on a different machine, and the result is deserialized back into your call site — with the network hop hidden from the caller.

This is older than REST. Sun's RPC (ONC RPC) shipped in the 1980s; CORBA and Microsoft's DCOM chased the same idea across languages and vendors in the 1990s; Java RMI did it for the JVM. REST arrived in 2000 as a reaction to how heavy and vendor-locked that generation had become — modeling the world as *resources* you `GET`/`POST`/`PUT` instead of *actions* you invoke. Both ideas are still very much alive today; they just solve different problems.

Mobile analogy: think of RPC as calling a delegate method where the delegate object happens to live on another machine. REST is closer to fetching and updating a record through a URL. Neither is "wrong" — they're different mental models for the same underlying job: getting two programs to talk.

2Anatomy of a call

Strip away any specific framework's branding and every RPC system is built from the same four pieces:

PieceJob
IDL (Interface Definition Language)A language-neutral contract describing the available methods and message shapes — gRPC's .proto, Thrift's .thrift.
Codegen: stub & skeletonA compiler reads the IDL and generates a client-side stub (looks like a local function, actually makes the network call) and a server-side skeleton (receives the call, invokes your real handler). This is what makes it feel local.
MarshallingConverting in-memory objects into bytes for the wire, and back again on the other end. Binary formats (Protobuf, Thrift's compact protocol) are smaller and faster to pack/unpack than JSON text.
TransportThe actual network layer underneath — HTTP/2 for gRPC, raw TCP or HTTP for Thrift, plain HTTP/1.1 for JSON-RPC.

Run this to see the stub do its job — from the caller's side it's one line, but the stub is quietly doing marshal → "send" → "server handles it" → unmarshal underneath:

JavaScript · runnable
// The "server": your actual business logic, oblivious to the network
const serverHandlers = {
  getUser: (id) => ({ id, name: 'Gokul', plan: 'pro' }),
};

// The "stub": generated code that makes a remote call look local
function makeStub(handlers) {
  return new Proxy({}, {
    get(_, method) {
      return (...args) => {
        const wireBytes = JSON.stringify({ method, args }); // 1. marshal
        console.log('→ sending over the wire:', wireBytes);
        const response = handlers[method](...args);            // 2. "network hop" + server executes
        const unmarshalled = JSON.parse(JSON.stringify(response)); // 3. unmarshal
        return unmarshalled;
      };
    },
  });
}

const userService = makeStub(serverHandlers);

// 4. Calling code never sees any of the above — it just calls a function
console.log('caller sees only:', userService.getUser(42));
The whole value proposition is in that last line. The caller wrote userService.getUser(42) — no URL, no HTTP verb, no manual JSON parsing. Every RPC framework, from 1980s ONC RPC to today's gRPC, exists to make that line possible.

3Where RPC quietly runs your day

You've almost certainly triggered dozens of RPC calls today without ever seeing the word "RPC":

What you didWhat's actually happening underneath
Ordered food or booked a rideThe order, payment, driver-matching, and notification services are almost certainly separate backends calling each other over an internal RPC framework — often gRPC — many times to fulfil one tap.
Connected a crypto wallet (MetaMask, etc.) to a dAppThe wallet talks to a blockchain node using JSON-RPC — eth_getBalance, eth_sendTransaction are literal RPC method names sent as JSON over HTTP. This is the de facto standard across Ethereum and most EVM chains.
A Kubernetes cluster scheduling a podThe kubelet talks to the container runtime (containerd, CRI-O) over gRPC via the CRI (Container Runtime Interface); etcd, the datastore behind the whole cluster's state, exposes its official client API as gRPC (etcd v3 API).
Traffic flowing through a service mesh (Envoy, Istio)Envoy's control-plane configuration protocol, xDS, is itself gRPC — the proxy that routes your traffic is, underneath, an RPC client.
Using enterprise software at a bank or telcoA meaningful amount of back-office integration still runs on RPC's earlier generation — Java RMI, CORBA, .NET Remoting/WCF — systems built in the 1990s–2000s that are still in production today.

5Why teams reach for it

  • It reads like code you already write. A typed method call is a lower cognitive tax than assembling a URL, a verb, headers, and a JSON body by convention.
  • Contracts catch bugs before runtime. A typo'd field name or wrong type fails at compile time against the generated stub, instead of surfacing as a silent undefined deep in production.
  • Performance, at scale. Binary encoding plus a multiplexed transport (HTTP/2 for gRPC) beats JSON-over-HTTP/1.1 meaningfully once you're making thousands of internal calls per second.
  • Streaming is native, not bolted on. Long-lived, bidirectional data flows (covered in depth in The Gateway's gRPC section) are a first-class call shape, not a workaround.
  • Polyglot by design. Codegen means a Python client calling a Go service is exactly as natural as calling within one language — nobody hand-writes the client library.

6The tradeoffs

  • Harder to debug by hand. You can't just open a browser network tab or curl an endpoint and read the response — binary payloads need dedicated tooling (grpcurl, protoc --decode) before a human can make sense of them.
  • No free HTTP caching. Every RPC call typically rides as an HTTP POST underneath, so the standard browser/CDN caching that a REST GET gets for free doesn't apply.
  • Tighter coupling than it looks. Client and server compile against the same contract. Rename or renumber a field carelessly and you can deploy a server that silently breaks every client still running the old stub.
  • Extra infrastructure for public/browser use. Since browsers can't speak raw gRPC, you need a translating layer (gRPC-Web + a proxy) the moment a browser client needs in — another component to run and secure.

That "tighter coupling" point is the one that bites teams for real — schema evolution has real, learnable rules. Run this to see the difference between a safe change and a breaking one:

JavaScript · runnable
// An OLD client, compiled against an earlier schema version
function oldClientReads(serverResponse) {
  return { id: serverResponse.id, name: serverResponse.name };
}

// ✅ SAFE evolution: the server ADDED a new field ("plan").
// The old client simply doesn't know to look for it — no crash.
const serverV2Response = { id: 42, name: 'Gokul', plan: 'pro' };
console.log('field added, old client still works:', oldClientReads(serverV2Response));

// ❌ BREAKING evolution: the server RENAMED "name" to "fullName".
// The old client's stub still asks for the field number/name it
// was compiled against — that data is simply gone now.
const serverV3ResponseRenamed = { id: 42, fullName: 'Gokul', plan: 'pro' };
const broken = oldClientReads(serverV3ResponseRenamed);
console.log('field renamed, old client silently loses data:', broken);
console.log(broken.name === undefined ? '⛔ name is undefined — this ships a real bug' : 'ok');
The rule that saves you: in Protobuf and Thrift, once a field number ships, treat it as permanent. Add new fields with new numbers; never reuse, renumber, or repurpose an old one. Deleting a field is safer than renaming it — a rename is a silent data-loss bug wearing a refactor's clothes.

7Vulnerabilities & security pitfalls

RPC's convenience hides real, well-documented risk if a team treats it as "just internal, so it's safe":

  • Reflection left on in production. gRPC's server reflection service — meant for local debugging with tools like grpcurl — hands back the entire list of methods and message schemas to any caller who can reach the port, if left enabled. That's a free map of your internal API surface to anyone who gets network access, no source code required. Disable it outside development.
  • Insecure-by-default during local dev. Most gRPC client libraries make you explicitly choose transport security, and it's common (and convenient) to disable it for local testing. The failure mode is that plaintext config quietly making it to a production deploy because "it worked locally."
  • The "trusted internal network" fallacy. Because RPC ports usually aren't browser-facing, teams often skip real authorization on service-to-service calls, assuming only their own services can reach them. Once an attacker lands on any host inside that network, the same broad, typed, easy-to-call surface that makes RPC pleasant for your own engineers makes lateral movement between services easier for an intruder too — the RPC-shaped version of SSRF pivoting.
  • Protocol-level exposure via the transport. Because gRPC rides on HTTP/2, it inherits HTTP/2's own vulnerabilities. The HTTP/2 Rapid Reset technique (CVE-2023-44487, disclosed October 2023 by Google, Cloudflare, and AWS together) rapidly opened and cancelled streams to power some of the largest DDoS attacks ever recorded — every HTTP/2 server implementation, gRPC included, needed patching, regardless of what sat above the transport.
  • Binary parsing is still attack surface. Like any binary deserializer, generated Protobuf/Thrift parsers can have bugs. A malformed or adversarial payload hitting a parsing edge case can crash a service (denial of service) even without achieving a full exploit.
Mental model: RPC gives you a typed, efficient phone line between services — it says nothing about who's allowed to call. Authentication (mTLS, tokens) and authorization are always a layer you add on top, the same way The Vault and The Gatekeeper require it everywhere else.

9Quick checklist

  • ✅ IDL treated as a permanent contract — new fields get new numbers, nothing is renumbered or renamed after shipping.
  • ✅ Reflection/introspection disabled outside local development.
  • ✅ Transport security (mTLS/TLS) explicit and verified in every environment, not just assumed from "it's internal."
  • ✅ Authorization checked on every RPC call, not waved through because the network is "trusted."
  • ✅ Debugging tooling (grpcurl or equivalent) in the team's kit before it's needed at 2am.
  • ❌ Don't expose an RPC service directly to a browser — put gRPC-Web and a proxy in front, or expose REST/GraphQL instead.
  • ❌ Don't assume "internal only" means "no auth needed."

10Key takeaways

RPC isn't a competitor to REST so much as a different answer to a different question — REST asks "what resource, what verb," RPC asks "what function, on what machine." It's the quiet default behind an enormous share of the infrastructure you already depend on daily, from the blockchain node your wallet talks to, to the container runtime scheduling the backend behind almost any app on your phone. The convenience of "it feels like a local call" is real and worth having — as long as you remember that a local-feeling call still crosses a real network, still needs real authorization, and still inherits every vulnerability of the transport underneath it.
