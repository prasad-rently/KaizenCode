♿ The Ramp

Building software that works when you can't see the screen, can't use a mouse, or can't hear the audio — not as charity, but as engineering that quietly makes the product better for everyone. Real WCAG math, real legal stakes, and the honest limits of automated tools.

1The problem, with no jargon at all

Try this thought experiment: use the app you're building right now with your eyes closed, navigating only by keyboard, with a piece of software reading the screen aloud to you. Or with one hand in a cast, unable to use a mouse at all. Or completely muted, in a meeting, trying to follow a video with no captions. For a meaningful share of your actual users — not a hypothetical edge case — that thought experiment is just Tuesday. Accessibility engineering is the discipline of making sure the product still works in every one of those situations.

This is the whole problem, restated once: most software is built and tested by people looking at a screen, holding a mouse or a touchscreen, with sound on. The moment any one of those assumptions breaks — visually, physically, or situationally — an inaccessible product simply stops working for that person. Accessibility is the engineering practice of not building on those assumptions in the first place.

2Who this is actually for

It's tempting to file accessibility under "features for a small group of users with permanent disabilities." The more useful framing, borrowed from physical architecture, is the curb-cut effect: the sloped curb cut built into a sidewalk was designed for wheelchair users, but it turns out to help parents with strollers, delivery workers with hand trucks, travelers with rolling luggage, and anyone on a bike — a huge population that was never the original target. Software accessibility works the same way:

Built forAlso quietly helps
A screen-reader user who is blindVoice-assistant users, SEO crawlers, anyone using a low-bandwidth text browser
Someone with a broken arm who can't use a mouse (temporary)Power users who prefer keyboard shortcuts for speed

3Semantic HTML: the foundation everything else builds on

The single highest-leverage decision in accessibility is almost embarrassingly simple: use the HTML element that actually means what you want, instead of a generic <div> styled to look like it. A real <button> comes with keyboard support, focusability, and an announced role built into the browser for free. A <div onclick="..."> styled identically has none of that — a sighted mouse user can't tell the difference; a screen reader or keyboard-only user hits a wall.

JavaScript · runnable
// What assistive tech actually perceives — not what it looks like on screen
const divAsButton = {
  tag: 'div',
  role: null,             // no implicit role — invisible as "a control" to a screen reader
  focusable: false,        // not in the Tab order at all, unless extra work is added
  keyboard: null,          // pressing Enter or Space does nothing
};

const realButton = {
  tag: 'button',
  role: 'button',          // implicit, free
  focusable: true,          // automatically part of the Tab order
  keyboard: 'Enter/Space triggers click', // built in, no JS needed
};

function report(el) {
  console.log(`<${el.tag}> → role: ${el.role ?? 'NONE'}, focusable: ${el.focusable}, keyboard: ${el.keyboard ?? 'NOT SUPPORTED'}`);
}

console.log('A <div onclick="..."> styled to look exactly like a button:');
report(divAsButton);
console.log('\nA real <button onclick="...">, same visual style:');
report(realButton);
console.log('\nBoth look identical on screen. Only one exists for a screen reader or keyboard user.');

4ARIA: powerful, and easy to make things worse with

ARIA (Accessible Rich Internet Applications) attributes let you explicitly tell assistive tech what a custom element is and how it behaves — role="button", aria-expanded="true", aria-label="Close menu". It exists for the cases semantic HTML genuinely can't cover: a custom dropdown, a tab panel, a live-updating notification region.

The accessibility community's own first rule of ARIA is "don't use ARIA." Meaning: reach for it only after native HTML can't do the job. A wrongly-applied role or a stale aria-expanded that never updates doesn't just fail to help — it actively lies to a screen reader, which is worse than adding nothing at all. ARIA is a promise about behavior; breaking that promise is worse than never making it.

5Keyboard navigation: the test that catches the most bugs

Unplug your mouse and try to use your own product with only Tab, Shift+Tab, Enter, and arrow keys. Two failure modes show up constantly: focus order that doesn't match visual order (CSS reordered things visually, but the underlying document order didn't move, so Tab jumps around unpredictably), and focus traps (a modal or menu that, once opened, never lets Tab escape it, stranding a keyboard user inside).

JavaScript · runnable
const goodOrder = ['Skip to content', 'Search', 'Nav: Home', 'Nav: About', 'Main content'];
// Visually, "Footer link" was moved up top with CSS — but the DOM order,
// which is what Tab actually follows, was never updated to match.
const brokenOrder = ['Nav: Home', 'Footer link', 'Search', 'Main content'];

function simulateTabs(order, count) {
  return Array.from({ length: count }, (_, i) => order[i % order.length]).join(' → ');
}

console.log('Good — Tab order matches what a sighted user sees on screen:');
console.log(simulateTabs(goodOrder, 4));

console.log('\nBroken — visually reordered with CSS, DOM order left untouched:');
console.log(simulateTabs(brokenOrder, 4));
console.log('A mouse user never notices this bug exists. A keyboard-only user hits it immediately.');

6Color contrast: real math, not a guess

"Does this text look readable to me" is not a test — low-vision users and situational glare need an actual, measurable margin. WCAG defines a precise contrast-ratio formula based on relative luminance, and a normal-text minimum of 4.5:1 for the "AA" level most legal standards reference. Run this with the exact WCAG formula to see how easy it is to fail without realizing it:

JavaScript · runnable
// The real WCAG 2.x relative luminance + contrast ratio formula
function luminance([r, g, b]) {
  const vals = [r, g, b].map((c) => {
    c /= 255;
    return c <= 0.03928 ? c / 12.92 : Math.pow((c + 0.055) / 1.055, 2.4);
  });
  return 0.2126 * vals[0] + 0.7152 * vals[1] + 0.0722 * vals[2];
}
function contrastRatio(rgbA, rgbB) {
  const [L1, L2] = [luminance(rgbA), luminance(rgbB)];
  const [lighter, darker] = L1 > L2 ? [L1, L2] : [L2, L1];
  return (lighter + 0.05) / (darker + 0.05);
}

const white = [255, 255, 255];
const lightGray = [200, 200, 200]; // a very common "looks fine to me" mistake
const darkerGray = [90, 90, 90];

const ratio1 = contrastRatio(white, lightGray);
const ratio2 = contrastRatio(white, darkerGray);

console.log('White background + light gray text (#C8C8C8):', ratio1.toFixed(2) + ':1');
console.log('  WCAG AA needs 4.5:1 for normal text →', ratio1 >= 4.5 ? 'PASS' : 'FAIL ⛔');
console.log('\nWhite background + darker gray text (#5A5A5A):', ratio2.toFixed(2) + ':1');
console.log('  WCAG AA needs 4.5:1 for normal text →', ratio2 >= 4.5 ? 'PASS' : 'FAIL ⛔');
Never rely on color alone, either. A red vs. green error/success indicator with no icon or text label is invisible to the roughly 1 in 12 men with red-green color blindness — pair color with a shape, icon, or text every time.

7How assistive tech actually reads a page

Browsers build a second, parallel tree alongside the visual DOM — the accessibility tree — made of each element's computed role, name, state, and value. A screen reader never sees pixels; it reads directly from this tree. Semantic HTML (§3) and correct ARIA (§4) are, together, exactly the mechanism that determines what ends up in that tree. Get either wrong, and the visual page can look perfect while the accessibility tree underneath is empty, wrong, or misleading.

8Mobile accessibility has its own specifics

iOS's VoiceOver and Android's TalkBack are the mobile equivalents of a desktop screen reader, and they bring platform-specific requirements: every interactive control needs an accessible label (an icon-only button with no accessibilityLabel is announced as nothing useful at all), and touch targets need real minimum size — the same 44×44pt (iOS) / 48×48dp (Android) guidance covered in Device Fragmentation exists precisely so a person with limited fine motor control can actually hit the button. Respecting the OS's dynamic type / font-scaling settings, rather than hardcoding pixel font sizes, is the mobile equivalent of the contrast work in §6.

9The real-world stakes

This isn't a hypothetical compliance category. Lawsuits and demand letters citing inaccessible websites under the US Americans with Disabilities Act (ADA) are filed by the thousands every year, and WCAG (Web Content Accessibility Guidelines) is the standard courts and regulators consistently point to when deciding whether a site is accessible "enough." The EU's European Accessibility Act extends similar requirements across a wide range of digital products and services. The same engineering-vs-checkbox distinction The Registrar makes about GDPR applies here word-for-word: "we're accessible" is a sentence a lawyer can write; whether it's actually true is an engineering question.

10The honest limits

  • Automated tools catch a fraction of real issues. Tools like axe and Lighthouse are genuinely useful and free — but they can mechanically verify things like contrast ratios and missing labels, not whether a screen reader experience actually makes sense as a whole. They're a floor, not a ceiling; real coverage needs an actual person, ideally someone who uses assistive technology daily, testing the real flow.
  • "Accessibility overlay" widgets are widely distrusted by the accessibility community. Third-party scripts that promise to auto-fix a site's accessibility by injecting JavaScript over the top of existing markup are, by broad practitioner consensus, unreliable at best and actively disruptive to real assistive-tech users at worst — they don't fix the underlying semantic HTML and ARIA problems this module covers.
  • Retrofitting is always more expensive than building it in. Exactly like security or testing, accessibility bolted on at the end costs far more than the same decisions made while a component is first being built.

11Quick checklist

  • ✅ Use real semantic HTML elements (button, nav, label) before reaching for ARIA or a styled div.
  • ✅ Tab through your own UI with the mouse unplugged — check order and confirm no focus traps.
  • ✅ Check text contrast with the real WCAG formula, not eyeballing it.
  • ✅ Never encode meaning in color alone.
  • ✅ Give every icon-only control (mobile or web) a real accessible label.
  • ❌ Don't add ARIA roles/attributes you don't intend to keep accurate as the UI changes.
  • ❌ Don't treat an automated scanner's green checkmark, or an overlay widget, as proof the product is actually accessible.

12Key takeaways

Accessibility engineering isn't a separate feature track bolted onto "real" product work — it's what happens when you stop assuming every user has full vision, a mouse, sound on, and perfect fine motor control. The curb-cut effect is the whole argument in one image: design for the person who genuinely can't use the default path, and you usually end up with something better for everyone standing behind them too.
