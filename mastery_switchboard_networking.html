🔀 The Switchboard

Every request you've ever made in this curriculum crossed a network you mostly ignored — Phase 1 treated it as a black box. This module opens the box: how a name becomes an address, what TCP and UDP actually trade off, why HTTP keeps reinventing its own plumbing, and how a load balancer decides which server gets your request.

1DNS resolution — a name becomes an address

Before a single byte of your request goes anywhere, the hostname has to resolve to an IP. That's a chain of caches and delegations, checked in order — each layer that answers saves a hop:

Browser cache → OS resolver cache → recursive resolver (ISP/8.8.8.8)
  → root server → TLD server (.com) → authoritative server → IP

Run the chain and see where a cold lookup actually spends its time versus a warm one:

JavaScript · runnable
// Simulated DNS resolution chain — each hop only runs on a cache miss
const cache = new Map();
function resolve(host) {
  if (cache.has(host)) return { ip: cache.get(host), hops: ['browser cache HIT'] };
  const hops = ['browser cache MISS', 'OS resolver MISS', 'recursive resolver → root', 'root → .com TLD', 'TLD → authoritative NS', 'authoritative → A record'];
  const ip = '203.0.113.' + (host.length % 255);
  cache.set(host, ip);
  return { ip, hops };
}
console.log('cold lookup:', resolve('api.example.com'));
console.log('warm lookup (same host):', resolve('api.example.com'));
console.log('→ TTL controls how long that warm hit lasts before the chain repeats');
RecordMaps to
A / AAAAHostname → IPv4 / IPv6 address
CNAMEHostname → another hostname (alias)
MXDomain → mail server, with priority
TXTArbitrary text — SPF/DKIM, domain verification
Mobile analogy: DNS's layered cache is the same idea as an app checking memory cache → disk cache → network — check the cheapest layer first, and a short TTL is the network equivalent of a cache-invalidation policy.

2TCP vs UDP — the reliability trade-off

TCP spends three packets before your data even starts moving, in exchange for guaranteed, ordered delivery. UDP skips the handshake and just sends — faster, but nothing guarantees the packet arrives, or arrives in order:

JavaScript · runnable
// TCP: handshake before any data. UDP: no handshake, no guarantee.
function tcpSend(payload) {
  const log = ['SYN →', '← SYN-ACK', 'ACK →', '  (connection established)', 'DATA: ' + payload + ' →', '← ACK'];
  return log;
}
function udpSend(payload, dropped) {
  return dropped ? ['DATAGRAM: ' + payload + ' → ', '  ✗ lost — nobody notices, nobody resends']
                 : ['DATAGRAM: ' + payload + ' → delivered, no ack expected'];
}
console.log('TCP (reliable, ordered):');
tcpSend('GET /orders').forEach(l => console.log('  ' + l));
console.log('');
console.log('UDP (fast, best-effort):');
udpSend('video frame #482', true).forEach(l => console.log('  ' + l));
console.log('→ a dropped video frame is fine to skip; a dropped payment request is not');
Use TCP when correctness matters more than latency (APIs, payments, file transfer). Use UDP when freshness matters more than completeness (live video, gaming, DNS queries themselves) — the receiver would rather skip a stale packet than wait for a resend.

3HTTP/1.1 → 2 → 3 — solving the same bottleneck three times

Each HTTP version exists to remove a head-of-line blocking problem the previous one introduced:

VersionTransportThe problem it fixes
HTTP/1.1TCPBaseline — one request per connection at a time (or several parallel connections as a workaround)
HTTP/2TCPMultiplexes many requests over one TCP connection — but one lost packet still blocks every stream (TCP head-of-line blocking)
HTTP/3QUIC (over UDP)Each stream is independent at the transport level — a lost packet only blocks its own stream, not the others

QUIC is why HTTP/3 rides on UDP instead of TCP: it reimplements reliability and ordering per-stream in user space, so it gets TCP's guarantees without TCP's single shared queue. It also folds the TLS handshake into the same round trip as the connection handshake, shaving a full round-trip off every new connection.

Multiplexing (HTTP/2+) is why mobile apps that batch dozens of small API calls into one connection stopped needing "domain sharding" tricks — the old HTTP/1.1 workaround of spreading requests across fake subdomains just to get more parallel connections.

4Load-balancing algorithms

A load balancer decides which backend server handles each request. The algorithm matters once servers aren't identical or connections aren't short-lived:

JavaScript · runnable
// Round-robin vs weighted vs least-connections, over 8 incoming requests
const servers = [{ name: 'A', weight: 1, conns: 0 }, { name: 'B', weight: 1, conns: 0 }, { name: 'C (bigger box)', weight: 2, conns: 0 }];

function roundRobin(n) {
  const picks = [];
  for (let i = 0; i < n; i++) picks.push(servers[i % servers.length].name);
  return picks;
}
function weighted(n) {
  const pool = servers.flatMap(s => Array(s.weight).fill(s.name));
  const picks = [];
  for (let i = 0; i < n; i++) picks.push(pool[i % pool.length]);
  return picks;
}
function leastConnections(n) {
  const load = { A: 3, B: 0, 'C (bigger box)': 1 }; // existing open connections
  const picks = [];
  for (let i = 0; i < n; i++) {
    const pick = Object.entries(load).sort((a, b) => a[1] - b[1])[0][0];
    load[pick]++; picks.push(pick);
  }
  return picks;
}
console.log('round-robin:      ', roundRobin(8).join(', '));
console.log('weighted (C=2x):  ', weighted(8).join(', '));
console.log('least-connections:', leastConnections(8).join(', '));
console.log('→ least-connections adapts to real load; round-robin assumes every request costs the same');

Consistent hashing is a fourth approach, used less for fairness and more for stickiness: hash the request key (a user ID, a cache key) onto a ring of servers, so the same key routes to the same server every time — critical for in-memory caches or sticky sessions, since adding/removing one server only reshuffles a small slice of the ring instead of everything.

5Anycast — one IP, many locations

Anycast advertises the same IP address from multiple physical locations over BGP, and routers naturally send each client to whichever advertiser is topologically closest — no DNS-based geolocation needed. It's how large CDNs and DNS resolvers (like 1.1.1.1) answer from a nearby point of presence everywhere on Earth using one address. The trade-off: if the nearest location goes down, BGP reroutes to the next-closest automatically, but a request already in flight to the failing location can be dropped mid-connection during the reroute.

6Connection pooling

A fresh TCP connection costs a handshake (and, for HTTPS, a TLS handshake on top) before any real data moves — paying that cost on every single request is the single most avoidable source of latency in a busy client or service. Connection pooling keeps a set of already-established connections open and reuses them across requests instead of tearing down and rebuilding:

JavaScript · runnable
// A tiny connection pool: reuse an idle connection instead of paying handshake cost again
class Pool {
  constructor(max) { this.max = max; this.idle = []; this.created = 0; }
  acquire() {
    if (this.idle.length) return { conn: this.idle.pop(), reused: true };
    this.created++;
    return { conn: 'conn#' + this.created, reused: false };
  }
  release(conn) { if (this.idle.length < this.max) this.idle.push(conn); }
}
const pool = new Pool(5);
for (let i = 0; i < 4; i++) {
  const { conn, reused } = pool.acquire();
  console.log('request ' + i + ' got ' + conn + (reused ? ' (reused — no new handshake)' : ' (new — paid the handshake cost)'));
  pool.release(conn);
}
console.log('total real connections created:', pool.created, 'for 4 requests');
This is why database drivers, HTTP clients (URLSession, OkHttp), and API gateways all pool connections by default — and why HTTP/2's multiplexing (§3) is, conceptually, connection pooling taken to its extreme: one physical connection serving unlimited concurrent logical streams.
