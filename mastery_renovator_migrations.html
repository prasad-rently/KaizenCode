🔨 The Renovator

Almost every real CTO job is inherited, not green-fielded — a system someone else built, under constraints you don't fully know, that has to keep serving live traffic while you change it underneath. Modernization done well is invisible to users; done badly, it's the outage that makes the news.

1The strangler fig — replace a system without a big-bang cutover

Named after the strangler fig vine that grows around a host tree until the original is gone, this pattern puts a routing facade in front of the legacy system, then migrates functionality piece by piece — each migrated piece gets routed to the new system, everything else still hits the old one — until eventually nothing routes to the legacy system anymore and it can be safely deleted:

JavaScript · runnable
// A strangler-fig router: route each endpoint to legacy or new, migrated one at a time
const migrated = new Set(['/checkout']); // only checkout has been rebuilt so far

function route(endpoint) {
  return migrated.has(endpoint) ? '→ NEW service' : '→ LEGACY monolith';
}
['/checkout', '/search', '/profile', '/checkout'].forEach(e => console.log(e + ' ' + route(e)));
console.log('');
console.log('...three months later, /search is rebuilt and migrated too...');
migrated.add('/search');
['/checkout', '/search', '/profile'].forEach(e => console.log(e + ' ' + route(e)));
console.log('→ the legacy monolith shrinks one endpoint at a time — never one risky cutover');
The facade is what makes this safe: users and other services never know which side of the fence a request landed on, and you can migrate — or revert — one endpoint at a time without touching the rest.

2Zero-downtime schema changes — expand/contract

A naive schema change (rename a column, change its type) locks or breaks the table while old code is still reading/writing the old shape. The safe pattern splits one risky change into several safe ones — expand, migrate, contract — never removing the old shape until everything reading it has moved on:

JavaScript · runnable
// Expand/contract: rename "name" → "full_name" with zero downtime, across 4 phases
let row = { name: 'Alex Chen' };

console.log('PHASE 1 — EXPAND: add the new column, keep the old one');
row.full_name = row.name; // backfill
console.log('  row now:', row, '(old code still reads/writes "name" safely)');

console.log('PHASE 2 — DUAL-WRITE: new code writes BOTH columns');
function writeDual(value) { row.name = value; row.full_name = value; }
writeDual('Alex Chen-Rivera');
console.log('  row now:', row, '(both old and new readers see correct data)');

console.log('PHASE 3 — MIGRATE READS: switch all readers to "full_name"');
console.log('  (no data change — just a code deploy; "name" is now unread but still written)');

console.log('PHASE 4 — CONTRACT: once nothing reads "name", stop writing it and drop the column');
delete row.name;
console.log('  row now:', row, '— migration complete, zero downtime the whole way');

3Dual-writes — the trap hiding inside phase 2

Writing to two places "at once" is never actually atomic — one write can succeed while the other fails, silently diverging the two copies. This is exactly the risk phase 2 above introduces, and it's why dual-writes need explicit handling, not just hope:

JavaScript · runnable
// Dual-write failure: the second write fails, and now the two copies disagree
let primary = { balance: 100 };
let secondary = { balance: 100 };

function unsafeDualWrite(amount, secondaryFails) {
  primary.balance += amount; // this write succeeds
  if (secondaryFails) throw new Error('secondary write failed (network blip, timeout, whatever)');
  secondary.balance += amount;
}
try { unsafeDualWrite(50, true); }
catch (e) { console.log('⛔ ' + e.message); }
console.log('primary.balance:  ', primary.balance, '(the write went through)');
console.log('secondary.balance:', secondary.balance, '(silently stale — nobody was told)');
console.log('');
console.log('→ safer alternatives: write to ONE source of truth and replicate via change-data-capture');
console.log('  (CDC/Debezium-style), or use an outbox pattern — never two independent application writes');
If you must dual-write, add a reconciliation job that periodically diffs the two copies and alerts on drift — dual-writes without reconciliation accumulate silent inconsistency for as long as the migration takes.

4Rewrite vs. refactor economics

The tempting move when inheriting a messy system is "let's just rewrite it from scratch, clean" — this is one of the most reliable ways to lose 6–18 months and end up with a system that has all-new bugs and none of the accumulated business-logic knowledge the old one quietly encoded. Netscape's full rewrite in the late '90s famously ceded the browser market to competitors while they rebuilt. The strangler fig above exists precisely because incremental replacement, done in production, almost always beats a big-bang rewrite:

Big-bang rewriteIncremental (strangler fig)
RiskAll-or-nothing — ships once, fails visiblySpread across many small, revertible steps
Business logicRe-derived from scratch — easy to lose edge casesPreserved; migrated piece carries its logic forward
Value deliveredNone until the whole rewrite shipsEach migrated piece ships value immediately
When it's rightThe old system is genuinely unsalvageable (rare)Almost every other case
Try it: (1) Pick one painful legacy endpoint and sketch what a strangler-fig facade in front of it would look like. (2) For a real column you'd like to rename or retype, write out the four expand/contract phases explicitly before touching anything. (3) If your system has any dual-write, check whether a reconciliation job actually exists — if not, that's live drift risk today. Deliverable: execute a zero-downtime column migration on a real (or phase) project, with traffic running throughout — expand, dual-write, migrate reads, contract.
