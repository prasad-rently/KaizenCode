🛟 The Ark

Phase 6 taught distributed systems concepts. The Ark is about surviving them going wrong at real scale — when one database can't hold your data anymore, when one region isn't enough, and when "we have backups" turns out to mean "we have files nobody has ever tried to restore."

1RTO and RPO — the two numbers that define your disaster budget

Before choosing any disaster-recovery architecture, decide two numbers explicitly: RPO (Recovery Point Objective) — how much data you can afford to lose, measured in time since the last safe copy — and RTO (Recovery Time Objective) — how long you can afford to be down while recovering. These aren't technical details; they're business decisions each additional "nine" costs real engineering effort to buy:

JavaScript · runnable
// Two DR strategies, same failure, very different RPO/RTO
function nightlyBackup() {
  const backupIntervalHrs = 24;
  const restoreTimeHrs = 3; // time to actually restore a full backup
  return { rpo: backupIntervalHrs + 'h (worst case: fail right before the next backup)', rto: restoreTimeHrs + 'h' };
}
function continuousReplication() {
  const replicationLagSec = 2;
  const failoverTimeSec = 30; // automated failover to the replica
  return { rpo: replicationLagSec + 's', rto: failoverTimeSec + 's' };
}
console.log('Nightly backup + manual restore:', nightlyBackup());
console.log('Continuous replication + auto-failover:', continuousReplication());
console.log('→ near-zero RPO/RTO costs real infrastructure (standby replicas, automated');
console.log('  failover) — the right answer depends on what an hour of data loss actually costs you');

2Sharding strategies

Once one database can't hold (or serve) all your data, you split it across many — sharding. The shard key decides how data is distributed, and a bad choice creates a hot shard that gets hammered while others sit idle:

JavaScript · runnable
// Hash-based sharding: a good hash spreads keys evenly across shards
function hash(s) { let h = 0; for (let i = 0; i < s.length; i++) h = (h * 31 + s.charCodeAt(i)) >>> 0; return h; }
const NUM_SHARDS = 4;
const users = Array.from({ length: 20 }, (_, i) => 'user_' + i);

function shardByHash(key) { return hash(key) % NUM_SHARDS; }
function shardByFirstLetter(key) { return key.charCodeAt(5) % NUM_SHARDS; } // naive/bad: skewed by naming pattern

const hashCounts = Array(NUM_SHARDS).fill(0);
const naiveCounts = Array(NUM_SHARDS).fill(0);
users.forEach(u => { hashCounts[shardByHash(u)]++; naiveCounts[shardByFirstLetter(u)]++; });

console.log('hash-based distribution across 4 shards:', hashCounts, '← fairly even');
console.log('naive key-derived distribution:      ', naiveCounts, '← can skew badly with real-world key patterns');
console.log('→ a hot shard means that one machine\'s capacity becomes your WHOLE system\'s ceiling');
Sharding also makes cross-shard queries (joins, aggregates across users) expensive or impossible without extra work — sharding is a trade of horizontal scale for query flexibility, not a free win.

3Cell-based architecture — containing blast radius

A traditional multi-tenant system shares infrastructure broadly: one bad deploy or one runaway query can degrade everyone. Cell-based architecture partitions the entire stack — not just the database, the whole deployment — into independent cells, each serving a fixed subset of users end-to-end. A failure in one cell only affects the users assigned to it:

JavaScript · runnable
// Blast radius: one failure in a monolith vs one failure in a cell-based system
const totalUsers = 100000;
const numCells = 10;

function monolithFailure() {
  return { affected: totalUsers, pct: '100%' };
}
function cellFailure() {
  const usersPerCell = totalUsers / numCells;
  return { affected: usersPerCell, pct: ((usersPerCell / totalUsers) * 100) + '%' };
}
console.log('monolith, one bad deploy fails everything:', monolithFailure());
console.log('10 cells, one cell fails:                ', cellFailure());
console.log('→ same bug, same bad luck — 10x fewer users affected, because failure was CONTAINED');
console.log('  not because it happened less often');
This is why large-scale systems (AWS itself is built this way internally) deliberately trade some efficiency for cell isolation — a smaller, guaranteed blast radius beats a lower failure rate with an unbounded one.

4Multi-region active-active

Running full application stacks live in multiple regions simultaneously — active-active — buys both lower latency (serve users from the nearest region) and resilience (an entire region outage only takes out its share of traffic, which reroutes to the others). The cost is a genuinely hard distributed-systems problem: if the same record can be written in two regions concurrently, you need a real conflict-resolution strategy (see The Homecoming's CRDTs) or you accept eventual consistency and design around it. Active-passive (one region live, one on standby) sidesteps that complexity at the cost of wasting the standby region's capacity most of the time, and a slower failover than active-active offers.

5Backup drills, capacity planning & load testing

A backup that's never been restored is a hypothesis, not a safety net — the only backup you can trust is one you've actually practiced restoring, on a schedule, with the time it took written down. Capacity planning is the same discipline applied ahead of time: model your predictable growth and traffic spikes (a product launch, a seasonal peak) before they arrive, and load testing is how you verify the system actually holds at that projected load rather than discovering the ceiling live, in production, during the spike itself.

Try it: (1) Find your last database backup and check when it was last actually restored and verified — not just taken. (2) Pick your busiest table and check what its shard key would be if you had to split it — would that key distribute evenly? (3) Draw your system as cells: if one instance/database/queue died right now, what fraction of users would actually be affected? Deliverable: run a restore-from-backup fire drill on a real project — actually restore from a real backup, time it, and document the RTO/RPO you observed versus what you assumed.
