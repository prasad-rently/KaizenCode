☸️ The Helmsman

Phase 4 taught you Docker — packaging one container. The Helmsman is about running hundreds of them reliably: restarting the ones that crash, spreading them across machines, scaling them under load, and rolling out a new version without anyone noticing. Kubernetes is the industry's answer to "now do that for real," and it's also frequently the wrong tool for a team that doesn't need it yet.

1The core object hierarchy

Four objects cover most of what you'll touch day to day, each wrapping the one below it with more resilience:

ObjectWhat it is
PodThe smallest deployable unit — one or more containers that always run together, sharing network and storage.
ReplicaSetKeeps N identical pods running — if one dies, it starts a replacement.
DeploymentManages ReplicaSets over time — this is how you actually roll out a new version, with a history to roll back to.
ServiceA stable network identity (one IP/DNS name) in front of a shifting set of pods — solves the problem of pods dying and getting new IPs constantly.

The controller pattern underneath all of them is the same idea, repeated everywhere in Kubernetes: you declare desired state, a controller loop constantly compares it to actual state, and reconciles the difference. Run it:

JavaScript · runnable
// The reconciliation loop: desired vs actual, converge every tick
let actual = ['pod-1', 'pod-2']; // one crashed already
const desired = 3;
let nextId = 3;

function reconcile() {
  if (actual.length < desired) {
    const pod = 'pod-' + nextId++;
    actual.push(pod);
    return 'started ' + pod + ' (actual ' + (actual.length - 1) + ' → ' + actual.length + ', desired ' + desired + ')';
  }
  if (actual.length > desired) {
    const killed = actual.pop();
    return 'terminated ' + killed + ' (too many replicas)';
  }
  return 'no action — actual (' + actual.length + ') matches desired (' + desired + ')';
}
for (let tick = 1; tick <= 3; tick++) console.log('tick ' + tick + ': ' + reconcile());
console.log('→ this loop never stops — it runs constantly, self-healing whatever drifts');

2Autoscaling — the same loop, driven by load

The Horizontal Pod Autoscaler (HPA) adjusts the desired replica count itself, based on a live metric (usually CPU%): more replicas when load rises, fewer when it falls, always aiming to keep per-pod utilization near a target. The Cluster Autoscaler does the same thing one layer up — adding or removing entire nodes (machines) when pods can't fit anywhere.

JavaScript · runnable
// HPA formula: desiredReplicas = ceil(currentReplicas * currentCPU / targetCPU)
function hpa(currentReplicas, currentCPU, targetCPU) {
  return Math.ceil(currentReplicas * (currentCPU / targetCPU));
}
const target = 50; // target 50% CPU per pod
[
  { replicas: 3, cpu: 50 },   // steady state
  { replicas: 3, cpu: 90 },   // traffic spike
  { replicas: 6, cpu: 20 },   // spike over, now over-provisioned
].forEach(s => {
  const want = hpa(s.replicas, s.cpu, target);
  console.log(s.replicas + ' pods @ ' + s.cpu + '% CPU (target ' + target + '%) → scale to ' + want);
});
console.log('→ scaling down is deliberately slower than scaling up, to avoid flapping');

3Service mesh — what a plain Service doesn't cover

A basic Service gives you load balancing and a stable name. It doesn't give you mutual TLS between every pod, fine-grained traffic splitting (send 5% of traffic to a new version), retries and circuit breaking at the network layer, or per-request observability across every hop. A service mesh (Istio, Linkerd) adds a sidecar proxy next to every pod that intercepts all traffic and handles those concerns uniformly — without your application code knowing the mesh exists.

A service mesh is real operational overhead — another moving part, another thing to upgrade, extra latency per hop. Reach for one when you genuinely need mTLS everywhere or fine-grained traffic control across many services; a handful of services usually doesn't need it yet.

4GitOps with Argo

GitOps flips the deployment model: instead of a CI pipeline pushing changes into the cluster, a controller (Argo CD, Flux) running inside the cluster continuously pulls the desired state from a git repo and reconciles — the same controller pattern from §1, now applied to your whole cluster's configuration. Git becomes the single source of truth: git revert is your rollback, and drift (someone kubectl edit-ing something by hand) gets silently corrected back to what's in git.

git push (new manifest) → Argo CD notices the diff → applies it to the cluster
someone manually kubectl-edits a Deployment → Argo CD notices drift → reverts it

5Canary rollouts — ship to 5% before ship to everyone

A canary rollout sends a small slice of real traffic to the new version, watches its error rate, and only proceeds if it looks healthy — catching a bad deploy while it can only hurt a few users instead of all of them:

JavaScript · runnable
// Canary rollout: ramp traffic in steps, abort on a bad error rate
function errorRateAt(pct) { return pct >= 50 ? 0.08 : 0.005; } // canary has a bug that only shows up under real load
const steps = [5, 25, 50, 100];
const threshold = 0.02; // abort above 2% errors
let aborted = false;
for (const pct of steps) {
  if (aborted) break;
  const err = errorRateAt(pct);
  if (err > threshold) {
    console.log(pct + '% canary → error rate ' + (err * 100) + '% exceeds ' + (threshold * 100) + '% → ABORT, roll back to stable');
    aborted = true;
  } else {
    console.log(pct + '% canary → error rate ' + (err * 100) + '% within threshold → proceed');
  }
}
console.log('→ the canary caught a bug that only appeared at real load, before it hit 100% of users');

6When Kubernetes is overkill

Kubernetes solves problems most teams don't have yet: hundreds of services, multiple teams deploying independently, workloads that genuinely need per-second autoscaling. If you're running a handful of services, a managed platform (Cloud Run, Fargate, App Runner, a single beefy server with Docker Compose) gets you 90% of the reliability with a fraction of the operational surface. Adopt Kubernetes when the coordination problem it solves is actually the problem you have — not because it's what "real" infrastructure looks like.

Try it: (1) Install minikube or kind and run kubectl get pods,deployments,services against it. (2) Write a Deployment manifest for one of your phase projects and apply it. (3) Scale it with kubectl scale and watch the reconciliation loop create/kill pods live. Deliverable: deploy a phase project to a local cluster and perform a canary rollout — shift traffic in steps, watch for errors, and either complete the rollout or roll it back.
