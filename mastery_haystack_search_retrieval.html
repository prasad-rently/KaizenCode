🌾 The Haystack

How search actually finds the needle — from a book's index at the back to the vector databases powering every RAG pipeline. The Oracle told you embeddings exist; this is how something actually finds the right one among millions.

1The problem, with no jargon at all

Imagine a library with ten million books and no card catalog. Someone asks "which book mentions octopuses?" — your only option is to open every single book and read it. That's obviously absurd at ten million books, but it's exactly what a naive search would do: compare the question against every document, one at a time. The entire field of search and retrieval exists to answer one question: how do you find the right handful of documents out of millions, in milliseconds, without reading all of them?

2The classic answer: an index, just like a book's

A textbook's index at the back doesn't list every sentence — it lists every important word, and next to each word, every page it appears on. Computer search does the exact same thing at a much larger scale: an inverted index maps each word to the list of documents containing it. A search for "cat sat" doesn't scan every document — it looks up "cat" and "sat" directly, in two fast lookups, and only considers documents that actually appear in at least one of those lists.

JavaScript · runnable
const docs = [
  'the cat sat on the mat',
  'the dog sat on the log',
  'cats and dogs are pets',
];

// Build the inverted index once: word → which documents contain it
const index = {};
docs.forEach((doc, id) => {
  doc.split(' ').forEach((word) => {
    if (!index[word]) index[word] = new Set();
    index[word].add(id);
  });
});

console.log('Documents containing "sat":', [...index['sat']]);
console.log('Documents containing "cat":', [...(index['cat'] || [])]);

// A query only touches the words it needs — never a full document scan
const candidates = new Set();
'cat sat'.split(' ').forEach((word) =>
  (index[word] || new Set()).forEach((id) => candidates.add(id))
);
console.log('\nQuery "cat sat" → candidate docs via index, zero full scans:', [...candidates]);

3Matching isn't enough — you need ranking

Finding which documents contain a word is the easy half. The harder question: of the thousand documents that contain "cat," which ones are actually about cats? The classic answer is TF-IDF (term frequency–inverse document frequency): a word that appears often in this document but rarely across the whole collection is a strong signal; a word that appears everywhere (like "the") is nearly worthless, no matter how often it shows up.

JavaScript · runnable
function termFrequency(term, doc) {
  const words = doc.split(' ');
  return words.filter((w) => w === term).length / words.length;
}
function inverseDocFreq(term, docs) {
  const containing = docs.filter((d) => d.includes(term)).length;
  return Math.log(docs.length / (1 + containing));
}
function tfidf(term, doc, docs) {
  return termFrequency(term, doc) * inverseDocFreq(term, docs);
}

const docs = [
  'the cat sat on the mat',
  'the dog sat on the log',
  'the cat and the dog are pets',
  'the birds fly over rooftops',
];

['the', 'cat', 'pets'].forEach((term) => {
  const score = tfidf(term, docs[2], docs);
  console.log(`"${term}" in doc 3 → TF-IDF score: ${score.toFixed(3)}`);
});
console.log('\n"the" appears in every document → its score goes NEGATIVE, actively unhelpful.');
console.log('"pets" appears in only one document → the highest, most distinguishing score.');
BM25, the ranking algorithm behind most production search engines (including Elasticsearch's default), is TF-IDF's more battle-tested successor — same core intuition, with extra tuning for document length and diminishing returns on repeated words.

4The new problem: when the words don't match, but the meaning does

Keyword search has a hard ceiling: a search for "affordable places to stay" will completely miss a document that says "budget accommodation," even though they mean the same thing. This is exactly the gap The Oracle introduced embeddings to close — turning text into a list of numbers (a vector) positioned so that texts with similar meaning end up as nearby points in space, regardless of which exact words were used. "Affordable places to stay" and "budget accommodation" land close together; "affordable places to stay" and "quantum physics" land far apart.

Finding the closest matches then becomes a geometry problem: given a query's vector, find the nearest vectors among millions of stored document vectors. This is what a vector database actually does underneath the term "semantic search."

5Why you can't just check every vector

The obvious approach — compute the distance from your query to every single stored vector, keep the closest ones — is called brute-force nearest neighbor, and it works perfectly. It also doesn't scale: checking a query against ten million vectors, for every single query, is far too slow for anything real-time. Run this to feel the scale of the problem, even at a tiny size:

JavaScript · runnable
// 1,000 toy "embeddings" as 2D points (real ones have hundreds of dimensions —
// 2D just makes the distance math easy to read here)
function randomVector() { return [Math.random() * 100, Math.random() * 100]; }
const vectors = Array.from({ length: 1000 }, randomVector);
const query = [50, 50];
function distance(a, b) { return Math.hypot(a[0] - b[0], a[1] - b[1]); }

let comparisons = 0, best = null, bestDist = Infinity;
vectors.forEach((v) => {
  comparisons++;
  const d = distance(query, v);
  if (d < bestDist) { bestDist = d; best = v; }
});
console.log('Brute-force nearest neighbor: checked EVERY vector →', comparisons, 'comparisons');
console.log('Best match:', best.map((n) => n.toFixed(1)), 'at distance', bestDist.toFixed(2));
console.log('\nThat was only 1,000 vectors. Real vector databases hold hundreds of');
console.log('millions — brute force at that scale is far too slow for a live query.');

6The real answer: approximate nearest neighbor search

Production vector databases (Pinecone, Weaviate, Milvus, Postgres's pgvector) don't check every vector — they trade a tiny, tunable amount of accuracy for an enormous speedup using Approximate Nearest Neighbor (ANN) algorithms. The dominant one today is HNSW (Hierarchical Navigable Small World): it organizes vectors into a multi-layer graph where the top layer has a few long-range connections — like highways between distant cities — and lower layers get progressively denser, like local streets. A search starts on the sparse top layer, jumps quickly toward the right neighborhood, then drops down layer by layer, taking smaller and smaller steps until it lands on a genuinely close match — all without ever touching most of the graph.

The trade being made explicitly: HNSW doesn't guarantee it finds the mathematically closest vector every time — it finds an excellent one, almost always, in a small fraction of the comparisons brute force needs. On real-world datasets of millions of vectors, that's routinely a reduction from millions of comparisons down to a few dozen graph hops — the entire reason semantic search over huge collections is fast enough to feel instant.

7Where this runs in production

SystemWhat it does
Elasticsearch / Apache LucenePowers a huge share of enterprise and website search, built on an inverted index with BM25 ranking by default.
Pinecone, Weaviate, MilvusPurpose-built vector databases — HNSW (or close relatives) under the hood, exposed as a simple "find similar vectors" API.
pgvectorAdds vector columns and ANN indexing directly to Postgres, so teams can add semantic search without standing up a separate database.
Any RAG pipeline (The Oracle)The "retrieval" step is exactly this: embed the user's question, run an ANN search against a store of pre-embedded document chunks, and hand the closest matches to the LLM as context.

8Hybrid search: using both

In practice, the strongest production search systems don't pick one approach — they run keyword (BM25) and vector search in parallel and merge the results. Keyword search catches exact terms, part numbers, and names that embeddings can blur together; vector search catches meaning and paraphrase that keyword search misses entirely. Most serious RAG and enterprise-search systems built today are hybrid for exactly this reason.

9The limits

  • Approximate means approximate. HNSW can occasionally miss the true best match in exchange for speed — usually an acceptable trade, but worth knowing when "why didn't it find the obviously relevant document" comes up.
  • Retrieval quality has a ceiling set by embedding quality. A vector search is only as good as the embedding model producing the vectors — the same "garbage in, garbage out" caution The Oracle raises about LLMs applies directly here.
  • Indexes aren't free to update. Inserting into a graph-based ANN index at high write-volume, in real time, is a genuinely harder engineering problem than appending to a simple list — a real operational cost as a collection grows and changes.

11Quick checklist

  • ✅ Use an inverted index for exact-term lookups — never scan every document.
  • ✅ Rank matches (TF-IDF/BM25), don't just return everything that matches.
  • ✅ Reach for vector search specifically when meaning matters more than exact wording.
  • ✅ Consider hybrid search before assuming vector-only is "better."
  • ❌ Don't assume ANN always finds the mathematically closest match — it's a deliberate, tunable trade-off.
  • ❌ Don't expect great retrieval from a mediocre embedding model — the ceiling is set upstream.

12Key takeaways

Search, at every scale, is the same core discipline: never read everything, build a structure that lets you skip almost all of it, and rank what's left so the best answer floats to the top. An inverted index does that for words; HNSW does the exact same thing, geometrically, for meaning. The "magic" behind a RAG pipeline finding the right paragraph out of a million isn't magic at all — it's this module, quietly running underneath.
