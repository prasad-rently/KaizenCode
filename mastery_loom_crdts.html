🧵 The Loom

CRDTs — data structures deliberately designed so that merging two conflicting copies always produces the same correct answer, automatically, no matter what order the merge happens in. How Figma, Notion, and a shared shopping cart all stay correct without ever asking a server to referee.

1The problem, picking up where detection left off

The Metronome ended on a pointed limitation: vector clocks can tell you two edits are concurrent — genuinely independent, neither one caused by the other — but they say nothing about what to actually do about it. Two people editing the same shared shopping list while both offline, each adding and removing items, will eventually reconnect. Detecting that their lists disagree is the easy half. Producing one final, correct list — automatically, without waking up an engineer or a user to arbitrate — is what this module is about.

This is the whole problem, restated once: can you design the data structure itself so that no matter what order two divergent copies get merged in, and no matter how many times you accidentally merge the same update twice, the result always converges to the one, single correct answer? A data structure with that property is called a CRDT — a Conflict-free Replicated Data Type.

2Why "last write wins" and "ask a human" don't scale

The offline-first sync article already covered the blunt options: last-write-wins (LWW) picks whichever edit has the later timestamp and silently throws the other one away — fine for a single field like "display name," disastrous for "list of items in your cart," where throwing away someone's addition means their item just vanishes with no error, no warning. Asking a human to manually resolve every conflict doesn't scale either — nobody wants a "which version of your shopping list did you mean?" dialog every time two devices sync.

CRDTs exist because there's a third option, specifically for structures shaped like counters, sets, and lists: design the merge rule so it's mathematically guaranteed to combine two versions correctly, every time, with no data loss and no human in the loop — for the shapes of data where that's actually possible.

3The core trick: make merging boring on purpose

Every CRDT follows the same underlying discipline, whether it's a counter or a full document: the merge operation has to work correctly no matter what order it's applied in, and applying the same update twice by accident can never make things worse. In plain terms — order shouldn't matter, and repeats shouldn't hurt. Once a data structure and its merge rule satisfy that, you can replicate it across any number of machines, let them diverge for as long as the network is down, and merging them back together is always safe.

4The simplest CRDT: a grow-only counter

Imagine three servers each counting "likes" on a post, and the network between them is unreliable. If they each kept one shared number and argued over whose number is "latest," you'd lose likes every time two servers updated concurrently. Instead, a G-Counter gives every replica its own private slot to increment — never anyone else's — and the true total is just the sum of every slot. Merging two versions is just taking the bigger number in each slot; you can never lose an increment, and merging the same state twice changes nothing.

JavaScript · runnable
function increment(counter, replicaId) {
  const next = { ...counter };
  next[replicaId] = (next[replicaId] || 0) + 1;
  return next;
}
function merge(a, b) {
  const ids = new Set([...Object.keys(a), ...Object.keys(b)]);
  const out = {};
  ids.forEach((id) => (out[id] = Math.max(a[id] || 0, b[id] || 0)));
  return out;
}
function total(counter) {
  return Object.values(counter).reduce((sum, n) => sum + n, 0);
}

// Server A and Server B both count likes while disconnected from each other
let serverA = increment(increment({}, 'A'), 'A'); // 2 likes came in on A
let serverB = increment({}, 'B');                       // 1 like came in on B
console.log('Server A saw:', serverA, '→ total', total(serverA));
console.log('Server B saw:', serverB, '→ total', total(serverB));

// Merge in either order — the result is identical either way
const mergedAB = merge(serverA, serverB);
const mergedBA = merge(serverB, serverA);
console.log('\nA-then-B merge:', mergedAB, '→ total', total(mergedAB));
console.log('B-then-A merge:', mergedBA, '→ total', total(mergedBA));
console.log('Merging the SAME state twice, by accident:', merge(mergedAB, serverA));
console.log('→ still correct. No likes lost, none double-counted, order never mattered.');

5A harder case: a set you can add to AND remove from

Counters only grow, which makes them easy. A shared shopping list needs both add and remove — and that's where a naive approach breaks: if Alice removes "milk" while Bob, at the same instant and unaware, re-adds "milk," which wins? An OR-Set (Observed-Remove Set) solves this with one clever trick: every add gets tagged with a unique ID, and a remove doesn't just say "milk is gone" — it says "remove exactly the tagged instances of milk I have personally seen so far." Any add that instance never observed — like Bob's concurrent re-add — survives the merge automatically, because the remove literally couldn't have been referring to it.

JavaScript · runnable
function add(set, item, tag) { return { ...set, [tag]: { item, removed: false } }; }
function remove(set, tag) {
  if (!set[tag]) return set; // can't remove a tag we never observed
  return { ...set, [tag]: { ...set[tag], removed: true } };
}
function merge(a, b) {
  const tags = new Set([...Object.keys(a), ...Object.keys(b)]);
  const out = {};
  tags.forEach((tag) => {
    const fromA = a[tag], fromB = b[tag];
    out[tag] = fromA && fromB
      ? { item: fromA.item, removed: fromA.removed || fromB.removed } // remove wins if EITHER saw it removed
      : (fromA || fromB);
  });
  return out;
}
function visible(set) {
  return Object.values(set).filter((e) => !e.removed).map((e) => e.item);
}

let alice = add({}, 'milk', 'milk#1');
let bob   = merge({}, alice); // Bob syncs, sees "milk#1" too, before going offline

// Now offline: Alice removes the milk she saw; Bob, unaware, re-adds a NEW milk
alice = remove(alice, 'milk#1');
bob   = add(bob, 'milk', 'milk#2');

console.log("Alice's list:", visible(alice));
console.log("Bob's list:  ", visible(bob));

const merged = merge(alice, bob);
console.log('\nMerged list:', visible(merged));
console.log("Milk survives — Bob's re-add used a NEW tag Alice's remove never saw.");
console.log('This is "add-wins" semantics, and it fell out of the design automatically.');
This is the classic "Amazon shopping cart" story. Amazon's own engineers wrote about exactly this shape of problem in their original Dynamo paper: when a cart replicates across data centers and diverges, the one thing you must never do is silently lose an item someone added. An OR-Set-style merge is precisely why "add wins" is the safe default for a cart, even though it can occasionally leave behind an item someone genuinely meant to delete.

6Collaborative text: the hardest everyday case

A shared document (Google Docs, Notion, Figma's text layers) needs something more elaborate than a set — order matters, and two people can type in the exact same spot at the same time. The trick text-focused CRDTs use is to give every single character a unique, permanent, sortable position identifier when it's typed — not "character 47," which shifts every time someone edits earlier in the document, but a stable identity tied to who typed it and what it was inserted between. Two concurrent insertions at "the same spot" get different, comparably-sortable identities, so they interleave into a deterministic, if not always intuitive, final order — without either character ever needing to know about the other at the moment it was typed.

You don't need to hand-build this. Real products use battle-tested libraries — Yjs and Automerge are the two most widely used JavaScript CRDT libraries, and both handle this exact text-merging problem so application engineers don't have to invent position identifiers themselves.

8The limits

  • Not every data type has a good CRDT. "Cancel this order if the total is under $50" is a business rule, not a mergeable data shape — CRDTs solve structural merging, not arbitrary application logic. Those conflicts still need the server-merge or manual-resolution strategies from the offline-sync article.
  • Tombstones accumulate. An OR-Set never truly forgets a removed item — it keeps a "removed" marker (a tombstone) so future merges still know it was deleted. Long-lived, high-churn CRDTs need a garbage-collection strategy or their metadata grows forever.
  • "Correct" doesn't always mean "intuitive." Add-wins semantics mean a delete can sometimes be quietly overridden by a concurrent add the deleter never saw — mathematically consistent, but occasionally surprising to a user who insists they deleted something.

9When to reach for one

10Quick checklist

  • ✅ Confirm the data shape actually fits a known CRDT pattern (counter, set, list) before reaching for one.
  • ✅ Use a maintained library (Yjs, Automerge) for anything text/document-shaped — don't hand-roll position identifiers.
  • ✅ Plan for tombstone growth on long-lived, high-churn sets.
  • ✅ Reserve CRDTs for genuinely concurrent, structural merges — not for enforcing business invariants.
  • ❌ Don't assume "add-wins" is always the intuitive outcome for users — document the behavior.
  • ❌ Don't build a custom CRDT from scratch when detecting-but-not-resolving (§1) is actually all you need.

11Key takeaways

CRDTs are what you get when you push the idea from The Metronome one step further: instead of just detecting that two things happened concurrently, design the data structure so merging concurrent versions is always safe, in any order, any number of times. That's not a trick that works for everything — but for the specific shapes of data that show up constantly in real products (counters, sets, collaborative documents), it's the difference between a shopping cart that never loses an item and a "sync conflict" dialog nobody wants to see.
