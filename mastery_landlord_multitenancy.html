🏢 The Landlord

Every SaaS product is a building with many tenants inside — the question is how much of the building each tenant actually shares. Share too much and one tenant's bad behavior (or a single missing filter in a query) leaks into everyone else's apartment. Isolate too much and you've built a hundred single-tenant products with a hundred times the operational cost. Multi-tenancy is choosing, deliberately, where that line sits.

1Pool, silo, and bridge — the three isolation models

ModelHow it worksTrade-off
PoolAll tenants share the same database and app instances; every row is tagged with a tenant_id.Cheapest to run and scale; isolation is only as strong as your query discipline.
SiloEach tenant gets fully separate infrastructure — its own database, sometimes its own app deployment.Strongest isolation and easiest to reason about; most expensive, hardest to operate at scale.
BridgeA hybrid — shared app tier but per-tenant databases (or the reverse), often reserved for large/regulated tenants.Isolation where it matters most, shared cost where it doesn't.

Most SaaS products start pooled for cost efficiency, then bridge their largest or most regulated tenants into silos as those customers demand it — you rarely choose one model for the product's entire lifetime.

2The pool model's classic bug — a forgotten tenant filter

Pooled multi-tenancy's entire security model rests on one thing: every single query that touches tenant data includes a WHERE tenant_id = ?. Forget it once, in one endpoint, and tenant A can read tenant B's data — this is one of the most common real-world SaaS data breaches, and it's purely a discipline failure, not a sophisticated attack:

JavaScript · runnable
// A shared "invoices" table — the tenant filter is the ENTIRE isolation boundary
const invoices = [
  { id: 1, tenantId: 'acme', amount: 500 },
  { id: 2, tenantId: 'acme', amount: 1200 },
  { id: 3, tenantId: 'globex', amount: 9000 }, // a competitor's invoice — must never leak
];

function buggyQuery() { // forgot the tenant filter
  return invoices;
}
function correctQuery(tenantId) {
  return invoices.filter(inv => inv.tenantId === tenantId);
}

console.log('acme calls the BUGGY endpoint (no tenant filter):');
console.log(buggyQuery());
console.log('  ⚠️  acme just saw globex\'s $9000 invoice — a real data breach');
console.log('');
console.log('acme calls the CORRECT endpoint (tenant filter applied):');
console.log(correctQuery('acme'));
console.log('→ this is why teams enforce tenant filtering at the ORM/query-builder level,');
console.log('  not by trusting every hand-written query to remember it');
Don't rely on developer discipline alone — enforce it structurally: row-level security policies at the database level, or a query-builder wrapper that makes it impossible to construct a tenant query without a tenant ID. The bug above should be a compile-time or database-level impossibility, not a code-review hope.

3Noisy neighbors

In a pooled model, one tenant running a huge batch export or an inefficient query can degrade response times for every other tenant sharing that database — the "noisy neighbor" problem. The fix is treating each tenant's resource consumption as something to actively bound, not just monitor after the fact:

JavaScript · runnable
// Per-tenant rate limiting protects everyone else from one heavy tenant
class TenantLimiter {
  constructor(limitPerMinute) { this.limit = limitPerMinute; this.usage = {}; }
  request(tenantId) {
    this.usage[tenantId] = (this.usage[tenantId] || 0) + 1;
    return this.usage[tenantId] <= this.limit;
  }
}
const limiter = new TenantLimiter(5); // 5 requests/min per tenant, independent of every other tenant

// "globex" runs a heavy batch job; "acme" makes a normal handful of requests
for (let i = 0; i < 8; i++) {
  const ok = limiter.request('globex');
  if (!ok) { console.log('globex request #' + (i + 1) + ' → 429 throttled (protects other tenants\' capacity)'); }
}
for (let i = 0; i < 3; i++) {
  const ok = limiter.request('acme');
  console.log('acme request #' + (i + 1) + ' → ' + (ok ? '200 OK (unaffected by globex)' : '429'));
}

4Per-tenant cost attribution

In a shared, pooled system, "how much does this tenant cost us to serve" isn't automatic — you have to actually measure it (compute time, storage, egress, support load) and tie it back to a tenant ID, or you're pricing blind. Without this, a whale customer running heavy queries on your cheapest plan can be quietly unprofitable for years before anyone notices:

JavaScript · runnable
// Per-tenant margin: measured cost to serve vs. what they actually pay
const tenants = [
  { name: 'acme',   plan: 'starter',  monthlyPrice: 99,  computeHrs: 2,   storageGB: 5   },
  { name: 'globex', plan: 'starter',  monthlyPrice: 99,  computeHrs: 180, storageGB: 900 }, // heavy usage, cheap plan
  { name: 'initech',plan: 'enterprise', monthlyPrice: 2500, computeHrs: 40,  storageGB: 200 },
];
const COMPUTE_COST_PER_HR = 0.5, STORAGE_COST_PER_GB = 0.1;

tenants.forEach(t => {
  const cost = (t.computeHrs * COMPUTE_COST_PER_HR) + (t.storageGB * STORAGE_COST_PER_GB);
  const margin = t.monthlyPrice - cost;
  console.log(t.name + ' (' + t.plan + ', $' + t.monthlyPrice + '/mo): cost to serve $' + cost.toFixed(2) + ' → margin $' + margin.toFixed(2) + (margin < 0 ? '  ⚠️  LOSING MONEY on this tenant' : ''));
});
console.log('→ without per-tenant attribution, globex\'s loss is invisible — buried in an average');
This is where The Bazaar's usage-based pricing becomes a technical necessity, not just a pricing preference: metering actual per-tenant consumption is the only way to price a heavy-usage tenant correctly instead of subsidizing them with everyone else's margin.

5The enterprise-readiness checklist

Before a large enterprise will sign, procurement and security teams typically require the same short list regardless of your product's actual functionality — build these in early rather than scrambling for a single deal:

  • SSO/SAML — enterprise identity providers (Okta, Azure AD), not just email/password.
  • Role-based access control (RBAC) — the enterprise's admin controls who on their side can see/do what.
  • Audit logs — a queryable record of who did what, when, for their own compliance needs.
  • Data residency — some regulated customers require their data to physically stay in a specific region.
  • SLA & uptime commitments — see The Fine Print on what you can honestly promise.
Try it: (1) In a real project, find every query that touches user/customer data and confirm each one filters by tenant/account ID — treat any that don't as a live bug. (2) Add a simple per-tenant rate limiter to an API endpoint. (3) Pick 3 fake tenants with different usage levels and compute their margin the way §4 does — would any of them lose you money at scale? Deliverable: add tenant isolation to a phase project — a tenant_id column enforced at the query layer, plus one test that proves tenant A cannot read tenant B's data.
