📱 The Homecoming

Every other module in this curriculum taught you the backend as a mobile engineer visiting foreign territory. This one is the trip home — the backend patterns that exist specifically because the client is a phone: flaky networks, app-store release cycles, battery constraints, and users who close the app mid-request and reopen it three days later on a different network entirely.

1The BFF pattern — one backend shaped for one client

A web client on broadband can afford to make five small API calls and stitch the results together in JavaScript. A mobile client on a spotty connection cannot — every round trip is a chance to fail, and battery/data cost real money to the user. The Backend For Frontend (BFF) pattern responds by giving each client type its own thin backend layer that aggregates and reshapes calls to the underlying services into exactly what that client needs, in one round trip:

JavaScript · runnable
// Without a BFF: the mobile client makes 3 round trips itself
function fetchProfile() { return { name: 'Alex' }; }
function fetchOrders() { return [{ id: 1 }, { id: 2 }]; }
function fetchNotifications() { return { unread: 4 }; }

console.log('WITHOUT a BFF — mobile client makes 3 separate round trips:');
console.log('  round trip 1 →', fetchProfile());
console.log('  round trip 2 →', fetchOrders());
console.log('  round trip 3 →', fetchNotifications());
console.log('');

// With a BFF: the aggregation happens server-side, mobile makes 1 round trip
function mobileHomeScreenBFF() {
  return { profile: fetchProfile(), orders: fetchOrders(), notifications: fetchNotifications() };
}
console.log('WITH a BFF — 1 round trip, shaped for exactly this screen:');
console.log(mobileHomeScreenBFF());
console.log('→ on a flaky network, 1 round trip that might fail beats 3 that might');
A web BFF and a mobile BFF talking to the same underlying services can legitimately return different shapes — the web dashboard might want paginated orders with full detail; the mobile home screen wants just the count and the 3 most recent. Each BFF exists to serve its client, not to be a generic API.

2Offline-first sync & CRDTs

A mobile app that only works with a live connection is a mobile app that fails constantly. Offline-first design writes to local storage immediately and syncs to the server when a connection appears — which creates a new problem: what happens when the same record was edited offline on two devices before either saw the other's change? A CRDT (Conflict-free Replicated Data Type) is a data structure designed so that merging two independently-edited copies always produces a sensible, deterministic result — no central lock, no "last write wins and silently discards the other edit" surprise:

JavaScript · runnable
// A G-Counter CRDT: each device tracks its OWN increments; merge = take the max per device
function merge(a, b) {
  const merged = { ...a };
  for (const device in b) merged[device] = Math.max(merged[device] || 0, b[device]);
  return merged;
}
function total(counter) { return Object.values(counter).reduce((a, b) => a + b, 0); }

// "likes" counter on a post, edited offline on two devices, no coordination between them
const phoneA = { phoneA: 3 };  // this device incremented 3 times while offline
const phoneB = { phoneB: 2 };  // this device incremented 2 times while offline, unaware of phoneA

console.log('phone A local state:', phoneA, '→ total', total(phoneA));
console.log('phone B local state:', phoneB, '→ total', total(phoneB));
const merged = merge(phoneA, phoneB);
console.log('merged (order-independent, no coordination needed):', merged, '→ total', total(merged));
console.log('→ merging B into A gives the same result as merging A into B — that\'s the CRDT guarantee');
Not every field can be a simple counter — text fields typically need a more complex CRDT (like an RGA or a Yjs/Automerge document) to merge concurrent edits character-by-character. Reach for a CRDT library rather than hand-rolling one for anything beyond counters and last-write-wins fields.

3Push notification infrastructure

At scale, push is a delivery pipeline: your backend enqueues a message, a fan-out worker batches device tokens, and each push goes through the platform gateway (APNs for iOS, FCM for Android) which owns final delivery and retry. The backend's job is token lifecycle (register, refresh, prune dead tokens on delivery failure) and backpressure — not retrying a flood of pushes into a gateway that's already rejecting them. See Silent push notifications for the client-side payload and platform-throttling details this module doesn't repeat.

4Release trains & phased rollouts

A web deploy reaches 100% of users in minutes; a mobile release reaches users over days as the app store reviews it, then as each user's phone decides to update. Two techniques compensate: a release train ships on a fixed cadence (every two weeks, whatever's ready gets on) so releases stay small and predictable instead of becoming rare, risky mega-releases; and a phased rollout exposes a new version to a small percentage of users first, watching crash rate before widening it — the same shape as a canary deploy, but gated by app-store adoption instead of a load balancer:

JavaScript · runnable
// Phased mobile rollout: widen the % only if crash-free rate holds
function crashFreeRateAt(pct) { return pct >= 50 ? 0.97 : 0.998; } // a device-specific crash only shows up at real scale
const steps = [1, 10, 50, 100];
const minCrashFree = 0.995;
let halted = false;
for (const pct of steps) {
  if (halted) break;
  const rate = crashFreeRateAt(pct);
  if (rate < minCrashFree) {
    console.log(pct + '% rollout → crash-free rate ' + (rate * 100).toFixed(1) + '% below ' + (minCrashFree * 100) + '% floor → HALT rollout, keep pinned at last-good %');
    halted = true;
  } else {
    console.log(pct + '% rollout → crash-free ' + (rate * 100).toFixed(1) + '% → widen');
  }
}
console.log('→ unlike a web canary, you cannot instantly roll back — halting just freezes the %,');
console.log('  the bad version stays on affected devices until the NEXT release fixes it');
This asymmetry — can't force an instant rollback — is why mobile teams lean harder on server-side feature flags and remote-config kill switches for risky client behavior: a flag your backend controls can be flipped off in seconds, even though the buggy code is already sitting on the device.

5Mobile observability

Web observability (The Watchtower) assumes you control the server the request runs on. Mobile observability has to work when you control neither the device nor its network — crash reporting (Crashlytics, Sentry) has to batch and upload after the fact since the crash killed the process, and every metric benefits from being sliced by app version and network condition (a spike in errors on 3.2.1 over cellular is a completely different signal than the same spike app-wide), since those are usually the actual cause.

Try it: (1) List every API call your app's home screen makes today — could a BFF collapse them into one? (2) Pick one piece of local state your app edits offline and decide whether last-write-wins is actually safe for it, or whether it needs a real CRDT. (3) Check whether your last mobile release used a phased rollout, and what crash-rate threshold would have halted it. Deliverable: write a design doc for the backend of an offline-first mobile app — the BFF shape, the sync/conflict strategy per data type, and the push and rollout plan.
