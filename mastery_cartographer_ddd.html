🗺️ The Cartographer

Every large codebase eventually has one object — User, Order, Product — that eleven different features have bolted fields onto until nobody fully understands it anymore. Domain-driven design is the discipline of drawing honest boundaries before that happens: naming the pieces the way the business actually talks about them, and refusing to let one model try to be everything to everyone.

1Ubiquitous language

DDD starts with a deceptively simple rule: the words in your code should be the exact words domain experts use, not a developer's paraphrase of them. If support agents say "ticket" and the database column is issue_id, that gap is where miscommunication — and bugs — breed. The fix isn't a glossary document; it's making the code itself use the real vocabulary, so a domain expert could read a class name and recognize their own business in it.

2Bounded contexts — the same word, different meanings

The insight that unlocks everything else: a large domain isn't one model, it's several, and the same word legitimately means different things in each. "Customer" in Sales (a lead, a deal size, a sales rep) is not the same "Customer" Support cares about (open tickets, SLA tier) — forcing them into one shared Customer class is how that object grows forty fields and nobody dares touch it. A bounded context is the explicit boundary where one model and its language are consistent — outside that boundary, the word can mean something else entirely, and that's fine:

JavaScript · runnable
// Same word, two legitimately different models — this is a feature, not a bug
const salesContext = {
  Customer(id) { return { id, dealSize: 42000, stage: 'negotiation', rep: 'Alex' }; }
};
const supportContext = {
  Customer(id) { return { id, openTickets: 2, slaTier: 'gold', lastContact: '2 days ago' }; }
};
console.log('Sales sees   Customer#9:', salesContext.Customer(9));
console.log('Support sees Customer#9:', supportContext.Customer(9));
console.log('');
console.log('→ trying to merge these into ONE shared Customer class is exactly how');
console.log('  you end up with a 40-field god object nobody fully understands');
Mobile analogy: this is the same reasoning behind feature modules — a ProfileModule and a CheckoutModule both touching "user," but each keeping its own view of what a user means to it, rather than one god User object every screen depends on.

3Entities, value objects & aggregates

Inside one bounded context, DDD distinguishes three kinds of objects: an entity has an identity that persists through change (an Order stays "the same order" even after its status changes); a value object has no identity — it's defined entirely by its data (two Money(10, 'USD') instances are simply equal, interchangeable); and an aggregate is a cluster of entities/value objects treated as one consistency unit, guarded by a single aggregate root that enforces the rules no one is allowed to break:

JavaScript · runnable
// The aggregate root is the ONLY door in — it enforces invariants on every change
class Order { // aggregate root
  constructor(id) { this.id = id; this.items = []; this.status = 'open'; }
  addItem(name, qty) {
    if (this.status !== 'open') throw new Error('cannot add items to a ' + this.status + ' order'); // invariant
    if (qty <= 0) throw new Error('quantity must be positive'); // invariant
    this.items.push({ name, qty });
  }
  ship() {
    if (!this.items.length) throw new Error('cannot ship an empty order'); // invariant
    this.status = 'shipped';
  }
}
const order = new Order('ord_1');
order.addItem('keyboard', 1);
order.ship();
console.log('order shipped:', order);
try { order.addItem('mouse', 1); }
catch (e) { console.log('blocked: ' + e.message); }
console.log('→ nothing outside Order can reach .items directly and break these rules');

4Hexagonal / clean architecture — the domain doesn't know about the database

Hexagonal architecture (ports & adapters) puts your domain logic at the center, depending on nothing external — it defines ports (interfaces it needs, like "a place to save an order"), and the outside world provides adapters that implement them (a real Postgres adapter in production, an in-memory adapter in tests). The dependency points inward: the database doesn't dictate how your domain models an order — your domain dictates what it needs, and the database adapts to that:

JavaScript · runnable
// Domain logic depends on a PORT (interface), never on a concrete adapter
function placeOrder(orderRepo, id, item) { // domain logic — knows nothing about Postgres or memory
  const order = { id, item, status: 'placed' };
  orderRepo.save(order);
  return order;
}

// Adapter A — in-memory (used in tests)
const memoryAdapter = { store: [], save(o) { this.store.push(o); } };
// Adapter B — pretend "Postgres" adapter (used in production)
const postgresAdapter = { save(o) { console.log('  [SQL] INSERT INTO orders VALUES (' + o.id + ', ' + o.item + ')'); } };

console.log('same domain function, swappable adapter:');
placeOrder(memoryAdapter, 'ord_1', 'keyboard');
console.log('  in-memory store now has:', memoryAdapter.store);
placeOrder(postgresAdapter, 'ord_2', 'mouse');
console.log('→ placeOrder() never changed — only the adapter plugged into the port did');
This is why "swap the database" is easy in a well-hexagonaled codebase and a multi-month project in most others — if domain logic imports the ORM directly, the database is the architecture, not a detail behind it.

5Context maps — how bounded contexts relate

Once you have multiple bounded contexts, you need to be explicit about how they depend on each other — a context map names the relationship instead of leaving it implicit:

PatternMeaning
Shared kernelTwo contexts deliberately share a small, tightly-coordinated piece of model — changes require both teams' agreement.
Customer/supplierOne context's team (supplier) builds what a downstream context (customer) needs — the downstream team has real influence over the API.
ConformistThe downstream context just accepts the upstream model as-is, with no influence — common when depending on a third-party or another org's system.
Anti-corruption layerA translation layer that converts an external or legacy model into your own clean domain model, so its mess doesn't leak inward.

An anti-corruption layer is the pattern to reach for most often when integrating with a legacy system or third-party API whose model doesn't match your own — better to translate at the boundary once than let a foreign shape spread through your whole domain.

Try it: (1) List the top 3–5 nouns in your domain (Order, Customer, Product…) and, for each, write down every team/feature that touches it — do their concerns actually differ enough to be separate bounded contexts? (2) Find one class in a real project that's grown fields for three or more unrelated purposes — that's a bounded-context violation in progress. (3) Pick one integration point with an external system and sketch what an anti-corruption layer for it would translate. Deliverable: re-draw an app you've built as a context map — the bounded contexts, their ubiquitous language, and the relationship (shared kernel / customer-supplier / conformist / ACL) between each pair.
