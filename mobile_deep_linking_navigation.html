🔗 Deep Linking: Getting Users to the Right Screen From Anywhere

A link that opens the app to its home screen instead of the thing the user tapped isn't a deep link — it's a broken promise. The plumbing that makes a link land on the right screen touches URL routing, the app store, and your navigation stack all at once.

Mobile Development · ~9 min read · updated August 2026

TL;DR — Prefer platform-verified HTTPS links (Universal Links / App Links) over custom URL schemes — they degrade gracefully to a web page when the app isn't installed, and they can't be hijacked by another app registering the same scheme. Deferred deep linking (surviving an app-store install round-trip) needs an extra matching step, since the OS gives you nothing for free across that gap. And every deep link handler needs a real answer for "the app was cold-launched with no navigation stack yet" — that's where most implementations quietly break.

1 · Three kinds of link, three different jobs

TypeExampleBehaviour
Custom URL schememyapp://product/42Opens the app directly if installed; otherwise the OS shows nothing useful — no fallback, and any app can register the same scheme.
Universal Link / App Linkhttps://example.com/product/42A real HTTPS URL the OS routes to your app if it's installed and the domain has verified ownership; otherwise it opens normally in the browser.
Deferred deep linkSame URL, tapped by a user with the app not yet installedSends the user through the store install flow, then (with extra plumbing) still lands them on the original screen after first launch.

2 · Why HTTPS links won over custom schemes

Custom schemes (myapp://…) were the original mechanism and still have their place for internal, app-to-app links you fully control — but they have two structural problems for anything public: no verified ownership (any app can claim myapp:// and hijack the traffic), and no fallback — tapping one with the app not installed does nothing useful, often silently.

Universal Links (iOS) and App Links (Android) fix both by using a real domain you provably own, verified through a well-known file the OS fetches once and caches:

apple-app-site-association · JSON
{
  "applinks": {
    "details": [{
      "appID": "TEAMID.com.example.app",
      "paths": ["/product/*", "/invite/*"]
    }]
  }
}

That file lives at https://example.com/.well-known/apple-app-site-association (Android's equivalent is assetlinks.json). Because ownership is cryptographically tied to a domain you serve, only your app can claim those paths — and because it's a real HTTPS URL, a user without the app simply lands on your website instead of a dead end.

Rule of thumb: use Universal/App Links for anything a user might tap from outside your app (email, SMS, another app, a QR code, social sharing). Reserve custom schemes for links your own app generates and consumes internally, where hijacking risk and the no-fallback problem don't apply.

3 · Deferred deep linking: bridging the install gap

The hard case: a user without the app taps a link, gets routed to the store, installs, and opens the app for the first time. By then the original URL is gone — first launch carries no memory of what was tapped, because the OS provides no built-in channel across an app-store install.

Every deferred-deep-linking approach is really a matching problem, closing that gap with some combination of:

  • Clipboard handoff — copy identifying data to the clipboard before redirecting to the store, read it back on first launch. Increasingly restricted by OS clipboard-privacy prompts.
  • Fingerprint matching — correlate the pre-install click (IP, user agent, timestamp) with the post-install first-open signal probabilistically. Imperfect and privacy-sensitive; treat matches as best-effort, not guaranteed.
  • A pending-action table server-side — store "this link was tapped, for this general context" keyed loosely, and reconcile it against the app's first authenticated request rather than trying to be exact about identity before the user has signed in.
Don't over-invest before measuring. Deferred linking is inherently probabilistic and often the least reliable link in the whole flow. Build the simple, verified case (app already installed) rock-solid first — it's most of the traffic — before spending real effort making the install-gap case marginally better.

4 · The part every implementation gets wrong: navigation state

A deep link can arrive in two completely different app states, and handling only one of them is the most common bug in this space:

StateWhat's already trueWhat has to happen
Warm startApp is already running, navigation stack exists, user is mid-session.Push the target screen onto the existing stack — but decide deliberately whether to preserve or clear what came before.
Cold startApp had zero navigation state; the deep link is the first thing that happens.Build a synthetic stack — target screen plus whatever ancestor screens back-navigation should logically lead to — not just the target screen floating alone with a dead-end back button.
Navigation handler · pseudocode
function handleDeepLink(url, appState) {
  const target = router.resolve(url);   // { screen: "product", params: { id: 42 } }

  if (appState.isColdStart) {
    // Build a full synthetic stack: Home → Category → Product,
    // not just "Product" floating with nowhere sensible to go back to.
    navigation.setStack(router.ancestorsFor(target).concat(target));
  } else {
    // Warm start: an explicit product decision — does this interrupt
    // the current flow, or queue until the user finishes what they're doing?
    navigation.push(target);
  }
}

Auth adds another layer: if the target screen requires sign-in and the deep link arrives before the user has authenticated, the link's destination has to survive the login flow and resume afterward — a link that silently drops its destination the moment auth is required trains users to distrust every link you send them.

5 · Quick checklist

  • ✅ HTTPS Universal/App Links for anything tapped from outside the app; custom schemes only for internal use.
  • ✅ Domain-verification file (apple-app-site-association / assetlinks.json) served correctly and cached-checked.
  • ✅ Deferred linking treated as best-effort, with the installed-app path made solid first.
  • ✅ Cold-start deep links build a real navigation stack, not a dead-end screen.
  • ✅ A deep link's destination survives an interrupting login flow.
  • ❌ Don't rely on a custom scheme as the only entry point for public/shareable links.
  • ❌ Don't assume the app is already running when you write the handler — write the cold-start path first.

6 · Key takeaways

Deep linking looks like a routing problem and is actually three problems stacked together: proving you own the URL, bridging the gap when the app isn't installed yet, and reconstructing navigation state the OS never guarantees you'll have. Get the verified, already-installed case right first — build cold-start navigation as a first-class path, not an afterthought — and the deferred-install case can stay best-effort without anyone noticing.
