📋 The Registrar

"We're GDPR compliant" is a sentence a lawyer can write; whether it's actually true is an engineering question. A user's data lives in a database, a cache, a search index, a log file, three analytics tools, and a nightly backup — deleting them "everywhere" is a pipeline you have to build, not a checkbox you can tick. This is The Vault's sibling: security keeps data from the wrong people; this module governs what you're allowed to keep, for how long, and how you prove it.

1GDPR & India's DPDP Act — the core rights

The two frameworks most engineers will encounter share the same backbone even though the terminology differs — GDPR calls the company a "controller/processor," India's Digital Personal Data Protection Act (DPDP, 2023) calls it a "Data Fiduciary," and the user a "Data Principal" — but the technical obligations converge on the same handful of rights:

RightWhat it requires you to build
AccessExport everything you hold about a user, in a readable format, on request.
Erasure ("right to be forgotten")Actually delete a user's data — not just hide it — across every system that holds it.
PortabilityExport in a structured, machine-readable format they can take to a competitor.
Consent withdrawalStop processing data the moment consent is withdrawn, not at the next convenient release.

None of these are legal-team deliverables — every one of them requires a real, working pipeline your team builds, tests, and maintains.

2Deletion pipelines — "everywhere" is more places than you think

A user's data is never in just one table. A real deletion request has to cascade through every system that might hold a copy, and the pipeline has to actually confirm each one, not assume:

JavaScript · runnable
// A real deletion request cascades across every system that might hold a copy
const systems = [
  { name: 'primary database', deletable: true },
  { name: 'search index', deletable: true },
  { name: 'analytics warehouse', deletable: true },
  { name: 'nightly backups (last 30 days)', deletable: false }, // can't delete from an immutable backup directly
  { name: 'third-party email tool', deletable: true },
];

function deleteUser(userId) {
  const results = [];
  systems.forEach(s => {
    if (s.deletable) results.push(s.name + ': ✅ deleted');
    else results.push(s.name + ': ⏳ flagged for deletion on next backup rotation (expires within retention window)');
  });
  return results;
}
deleteUser('user_42').forEach(r => console.log(r));
console.log('→ "deleted" for backups usually means "will age out within N days" — document that');
console.log('  explicitly, since regulators expect you to know exactly where every copy lives');
The most common real-world failure isn't malice, it's an untracked copy — a debug export, a support ticket attachment, a spreadsheet someone downloaded. A deletion pipeline is only as complete as your actual data inventory.

3Retention policies — data shouldn't live forever by default

The safest data is data you no longer hold — every record you keep past its useful life is pure liability with no offsetting benefit. A retention policy makes expiry automatic instead of "whenever someone remembers to clean up":

JavaScript · runnable
// Automated retention: purge records past their policy's TTL
const now = 1000; // "today", in days-since-epoch for simplicity
const POLICY_DAYS = { 'support_ticket': 365, 'login_log': 90, 'marketing_consent': 730 };
const records = [
  { type: 'support_ticket', createdAt: 400 },   // 600 days old
  { type: 'login_log', createdAt: 950 },        // 50 days old
  { type: 'login_log', createdAt: 700 },        // 300 days old — past policy
  { type: 'marketing_consent', createdAt: 500 },
];
records.forEach(r => {
  const ageDays = now - r.createdAt;
  const limit = POLICY_DAYS[r.type];
  console.log(r.type + ' (age ' + ageDays + 'd, limit ' + limit + 'd): ' + (ageDays > limit ? '🗑️  PURGE — past retention window' : '✅ keep'));
});
console.log('→ run this as a scheduled job, not a manual quarterly cleanup');

4SOC 2 / ISO 27001 — controls as code

Traditional compliance audits are a once-a-year manual scramble: screenshots, spreadsheets, someone frantically confirming every engineer with prod access still needs it. Controls as code treats each compliance requirement as an automated, continuously-running check — the same discipline as your test suite, applied to compliance instead of correctness:

JavaScript · runnable
// SOC 2 controls, automated: run continuously instead of once a year by hand
const systemState = {
  prodDbEncryptedAtRest: true,
  mfaEnforcedForAllAdmins: true,
  auditLogRetentionDays: 45, // policy requires 90+
  staleAdminAccounts: ['ex-employee@company.com'], // should have been revoked
};
const controls = [
  { id: 'CC6.1', name: 'Encryption at rest', check: () => systemState.prodDbEncryptedAtRest },
  { id: 'CC6.6', name: 'MFA for privileged access', check: () => systemState.mfaEnforcedForAllAdmins },
  { id: 'CC7.2', name: 'Audit log retention ≥ 90 days', check: () => systemState.auditLogRetentionDays >= 90 },
  { id: 'CC6.3', name: 'No stale privileged accounts', check: () => systemState.staleAdminAccounts.length === 0 },
];
let failures = 0;
controls.forEach(c => {
  const pass = c.check();
  if (!pass) failures++;
  console.log(c.id + ' ' + c.name + ': ' + (pass ? '✅ PASS' : '❌ FAIL'));
});
console.log('');
console.log(failures + ' of ' + controls.length + ' controls failing — caught by a nightly job, not next year\'s audit');
This is the same instinct as The Paved Road's DORA metrics — measure continuously, automatically, so drift is caught in days instead of discovered a year later by an outside auditor.

5Audit trails

An audit trail is an append-only, tamper-evident log of who accessed or changed what, when — required both to satisfy SOC 2/ISO 27001 auditors and, in practice, to actually investigate an incident (see The Storm Keeper). The two properties that make an audit log actually trustworthy: append-only (no one, including admins, can edit past entries) and separated from the systems it's watching (so compromising the main system doesn't let an attacker also erase their tracks).

Try it: (1) List every system that would need to receive a deletion request for one of your users — database, search, analytics, backups, third-party tools — and check whether a pipeline actually reaches all of them today. (2) Write one retention policy for a real data type in your system and check whether anything currently enforces it automatically. (3) Pick three SOC 2 Trust Services Criteria and write an automated check for each, the way §4 does. Deliverable: map SOC 2 controls onto a phase project — pick a real control category (access control, encryption, logging, change management) and document exactly how your project would satisfy it, with an automated check where possible.
