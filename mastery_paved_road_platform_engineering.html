🛤️ The Paved Road

Phase 4 taught you to set up CI/CD and infra once, for one project. Platform engineering is what happens when fifty teams each need that setup — do it fifty times, bespoke and drifting, or build one well-paved road that most teams can just drive on without thinking about the pavement.

1Why platform engineering exists

Early on, every engineer configuring their own CI, provisioning their own infra, and picking their own logging library is fine — there are only a few of them, and the variation is manageable. Past a certain size, that same freedom becomes a tax: onboarding takes weeks, every team's setup is subtly different, and incidents take longer to debug because nobody shares a mental model of "how deploys work here." A platform team's job is to absorb that complexity once, centrally, so product teams spend their time on product work instead of reinventing infrastructure.

2Internal developer platforms & golden paths

An Internal Developer Platform (IDP) — Backstage is the most common open-source example — is a self-service layer: a developer requests a new service, a database, or a deployment pipeline through the platform, and it provisions the pre-approved, pre-secured version automatically, instead of filing a ticket or hand-rolling Terraform. The golden path is the opinionated default that IDP presents — the well-tested, well-supported way to do the common thing:

JavaScript · runnable
// Golden path vs bespoke setup — time to first deploy for a new service
function bespokeSetup() {
  return [
    'write Dockerfile from scratch (2 days)', 'configure CI pipeline (2 days)',
    'provision infra by hand — tickets to platform/security teams (5 days)',
    'wire up logging/metrics conventions (1 day)', 'first deploy (day 10)'
  ];
}
function goldenPathSetup() {
  return [
    'run `platform new-service` — scaffolds Dockerfile, CI, infra, logging (10 min)',
    'fill in the one business-logic file', 'first deploy (day 1)'
  ];
}
console.log('BESPOKE:'); bespokeSetup().forEach(s => console.log('  ' + s));
console.log('');
console.log('GOLDEN PATH:'); goldenPathSetup().forEach(s => console.log('  ' + s));
console.log('→ 9 days saved is 9 days of product work, multiplied by every new service, forever');
A golden path becomes a golden cage the moment there's no escape hatch for the team with a genuinely unusual need. The healthiest platforms make the paved road the easy default while still allowing an informed team to go off-road — with the understanding that off-road means owning the consequences themselves.

3Monorepos, polyrepos & build systems

A monorepo puts every service/package in one repository with one shared build system; a polyrepo splits each into its own repo. The trade-off is coordination cost versus isolation: a monorepo makes cross-cutting refactors and shared-code changes atomic (one PR touches everything affected), but only if the build system can handle it — a naive "rebuild everything on every change" monorepo grinds a large org to a halt. Tools like Bazel, Nx, and Turborepo solve this with incremental, cached builds: only rebuild what actually changed, and its dependents:

JavaScript · runnable
// Incremental build: only rebuild a package if it (or a dependency) changed
const graph = { // package → its dependencies
  ui: ['core'], api: ['core', 'db'], core: [], db: []
};
const cache = { ui: 'hash_A', api: 'hash_B', core: 'hash_C', db: 'hash_D'}; // last successful build's hash
const changed = new Set(['core']); // only "core" was actually edited this commit

function needsRebuild(pkg, visited = new Set()) {
  if (visited.has(pkg)) return false;
  visited.add(pkg);
  if (changed.has(pkg)) return true;
  return graph[pkg].some(dep => needsRebuild(dep, visited));
}
Object.keys(graph).forEach(pkg => {
  const rebuild = needsRebuild(pkg);
  console.log(pkg + ': ' + (rebuild ? '🔨 REBUILD (depends on changed core)' : '⚡ CACHE HIT — unchanged, skip'));
});
console.log('→ "db" changed nothing and shares no dependency with core — its build is free');

4Measuring developer productivity — DORA

The DORA four keys (from Google's DevOps Research and Assessment team) are the closest thing the industry has to an objective, outcomes-based measure of engineering performance — deliberately choosing metrics that resist gaming individuals, since they measure the system, not the person:

MetricMeasuresElite benchmark
Deployment frequencyHow often you ship to productionOn-demand (multiple/day)
Lead time for changesCommit → running in production< 1 hour
Change failure rate% of deploys causing a production failure0–15%
Time to restore service (MTTR)How fast you recover from a failure< 1 hour

Compute them from a small sample of deploy/incident data — this is exactly the calculation to run against your own repo's history:

JavaScript · runnable
// DORA four keys from raw deploy/incident timestamps (hours since epoch, for simplicity)
const deploys = [
  { commitAt: 0, deployedAt: 3 }, { commitAt: 24, deployedAt: 26 },
  { commitAt: 48, deployedAt: 50 }, { commitAt: 72, deployedAt: 75 },
  { commitAt: 96, deployedAt: 98 }
]; // 5 deploys over 5 days
const incidents = [{ causedByDeployAt: 50, detectedAt: 50, resolvedAt: 52 }]; // 1 bad deploy, 2h to fix

const days = 5;
const deployFreq = (deploys.length / days).toFixed(1) + '/day';
const avgLeadTime = (deploys.reduce((sum, d) => sum + (d.deployedAt - d.commitAt), 0) / deploys.length).toFixed(1) + 'h';
const changeFailureRate = ((incidents.length / deploys.length) * 100).toFixed(0) + '%';
const mttr = (incidents.reduce((sum, i) => sum + (i.resolvedAt - i.detectedAt), 0) / incidents.length).toFixed(1) + 'h';

console.log('Deployment frequency: ', deployFreq, ' (Elite: on-demand / multiple per day)');
console.log('Lead time for changes:', avgLeadTime, '    (Elite: < 1 hour)');
console.log('Change failure rate:  ', changeFailureRate, '     (Elite: 0–15%)');
console.log('Time to restore (MTTR):', mttr, '   (Elite: < 1 hour)');

5SPACE — what DORA doesn't capture

DORA measures the delivery pipeline; it says nothing about whether engineers are burning out to hit those numbers. The SPACE framework broadens the lens: Satisfaction & well-being, Performance (outcomes, not output), Activity (raw volume — commits, PRs — useful only alongside other signals), Communication & collaboration, and Efficiency & flow (uninterrupted focus time). Use DORA to know if delivery is healthy; use SPACE to know if the humans producing that delivery are.

Never use any single metric from either framework — especially Activity (commit count, lines of code, PRs merged) — to evaluate individual engineers. That's precisely the kind of gaming (padding commits, splitting PRs artificially) these frameworks were designed to avoid by measuring team/system outcomes instead.
Try it: (1) Run git log --since="30 days ago" on a real repo and count actual deploys/merges to main to estimate deployment frequency. (2) Time how long it currently takes a new engineer to ship their first change — that's your real onboarding lead time. (3) If you have CI build times, check whether they scale with the whole repo's size or just what changed — that's the incremental-build question from §3. Deliverable: measure the four DORA metrics on your own repo, using real commit/deploy/incident history.
