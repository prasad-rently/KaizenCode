🔌 Offline-First Sync: Designing for the Network You Don't Have

Most mobile apps are built as if the network is always there and treat "offline" as an error state. Offline-first flips that: the local copy is the truth, and the network is just how two truths eventually agree.

Mobile Development · ~9 min read · updated August 2026

TL;DR — Write to local storage first and render instantly; queue the change for the server in the background. When the same record changes in two places before they can agree, you need an explicit conflict policy — last-write-wins for simple fields, CRDTs or server-side merge for anything collaborative. The hard part was never "detecting offline." It's deciding, in advance, who wins when two truths disagree.

1 · Online-first vs. offline-first, as architectures

An online-first app treats the server as the only source of truth: a screen shows a spinner, calls the API, and renders what comes back. Offline is handled — if at all — as a special error state with a "no connection" banner.

An offline-first app treats the local database as the source of truth for rendering. Every read comes from disk, instantly, whether or not the network is up. Every write goes to disk first, then to a queue that drains to the server whenever a connection exists. The network becomes a background concern instead of something the UI blocks on.

Mental model: in online-first, the network is on the critical path of every screen. In offline-first, the network is on the critical path of nothing — it's a background job that keeps the local copy honest.

2 · The write path: local first, sync later

The core shape is the same across iOS, Android, and React Native, regardless of which local database you use (SQLite, Core Data, Room, Realm, WatermelonDB):

Write path · pseudocode
function updateTodo(id, changes) {
  // 1. Write to local DB immediately — the UI reads from here
  db.update("todos", id, { ...changes, "_dirty": true, "_updatedAt": now() });
  ui.render();  // instant — no network in this path

  // 2. Enqueue a sync job; a background worker drains this queue
  // whenever connectivity + auth allow, independent of this call
  syncQueue.enqueue({ type: "update", table: "todos", id, changes });
}

Nothing about step 1 depends on the network being up. That single property is what "offline-first" buys you: the app feels the same whether the user is on fibre or in a lift.

3 · The queue has to survive a killed app

A sync queue kept only in memory is worthless — the OS can suspend or kill the app at any time, especially on a low-end device under memory pressure. The queue must be a durable, ordered log in the same local database as the data it describes, so a crash mid-sync leaves the system in a state it can resume from, not one it has to guess about.

  • Ordering matters. Two edits to the same record must replay in the order they happened, or the second can be silently overwritten by the first.
  • Idempotency matters more. The same job may run twice — once before a crash, once after resume, or once from a duplicate network retry. Give every job a stable ID and let the server de-duplicate by it.
  • Batch the drain. Sending one request per queued change is slow and battery-hungry; batch several jobs into one sync round-trip when the queue has more than a few pending.

4 · Conflicts: the part nobody wants to design for

The queue eventually catches up to the server — but what if the server's copy of that record also changed while the device was offline? Now two versions disagree, and something has to decide the outcome. There is no default-correct answer; it's a product decision disguised as an engineering one.

StrategyHow it decidesGood fit
Last-write-wins (LWW)Whichever edit has the newer timestamp overwrites the other, field by field or record by record.Simple settings, single-owner records (a user's own profile field).
Server-authoritative mergeThe server applies domain rules (e.g. "quantity can only decrease") and returns the resolved state; the client accepts it.Inventory, balances — anything with business invariants.
CRDTs (conflict-free replicated data types)The data structure itself is designed so concurrent edits merge mathematically without a decision — e.g. a grow-only counter, or an OR-Set for list membership.Collaborative editing, offline-tolerant counters/sets.
Operational Transform (OT)Edits are transformed against each other so intent is preserved regardless of arrival order.Real-time collaborative text (what Google Docs-style editors use).
Manual resolutionSurface both versions to the user and let them pick.High-stakes, low-frequency conflicts (a shared document rename).
Clocks lie. LWW is only as good as the clock behind the timestamp. A device with a skewed clock can make an old edit look newest and silently clobber a real change. Prefer a server-issued logical clock (a monotonic version number per record) over the device's wall clock whenever you can.

5 · Optimistic UI and the rollback you must plan for

Because the UI renders from local state before the server has confirmed anything, every optimistic write needs a defined failure path — not just a happy path:

Sync worker · pseudocode
async function drainQueue() {
  for (const job of syncQueue.pending()) {
    try {
      const result = await api.send(job);       // idempotency key = job.id
      db.reconcile(job.table, result);      // server's version wins on return
      syncQueue.markDone(job.id);
    } catch (err) {
      if (err.isConflict()) {
        db.applyResolution(job, err.serverVersion);  // §4's chosen strategy
      } else if (err.isRetryable()) {
        syncQueue.retryWithBackoff(job.id);         // leave "_dirty" set, try later
      } else {
        db.rollback(job);                          // e.g. 422 — undo the optimistic write
        ui.notify("Couldn't save that change");
      }
    }
  }
}

The three branches — reconcile, retry, rollback — are not optional extras. An optimistic UI without a rollback path is just a UI that lies to the user when the server disagrees.

6 · Detecting "online" is a trap; detecting "synced" is the real signal

A raw connectivity flag (NWPathMonitor, ConnectivityManager) tells you the radio is up — not that requests actually complete. Captive portals, VPN failures, and flaky cell towers all report "connected" while every request times out. Treat connectivity state as a hint to attempt a sync, and treat an actual successful round-trip as the only proof you have that syncing works right now. Surface "last synced 4 minutes ago" to the user, not "online"/"offline" — it's the honest signal and it degrades gracefully.

7 · Quick checklist

  • ✅ UI reads and writes local storage first; network is a background concern.
  • ✅ Sync queue is durable (on-disk), ordered, and every job has a stable idempotency key.
  • ✅ A named conflict strategy exists per data type — LWW, server-merge, CRDT, or manual — chosen deliberately, not by default.
  • ✅ Every optimistic write has a defined rollback, not just a happy path.
  • ✅ "Synced" state comes from a successful round-trip, not from a connectivity flag.
  • ❌ Don't use device wall-clock timestamps as your only conflict tiebreaker.
  • ❌ Don't let the sync queue live only in memory.

8 · Key takeaways

Offline-first isn't a network feature bolted onto an online app — it's a different default direction for data flow: local first, network as an eventually-consistent background sync. The engineering cost isn't in detecting "no internet"; it's in deciding, up front, who wins when two truths disagree — and building a queue durable enough to keep trying until they do.
